# 안정된 골격 — 공유 UI 레인 + 학습·동결 지도 (설계 확정)

- 작성: 2026-07-18
- 상태: **설계 확정 / 미구현** — 사용자와 함께 설계를 동결한다. 구현은 (a) 배선 세션(ADR-0054) 안착 + 조율 후, (b) 실사용 지터 통증 검증(아래 게이트) 이후. "왜 이렇게 결정했는지"를 남겨 나중에 바로 착수 가능하게 한다(프로젝트 원칙).
- 계보: [slot-reservation 메모](2026-07-18-structural-persistence-slot-reservation.md)를 이 문서로 통합·확장. tidy-tree는 이미 구현([ADR-0058](../decisions/0058-tidy-tree-centered-group-layout.md)).

## 0. 한 줄 목표

**개발자가 외울 수 있는, 코드가 바뀌지 않는 한 안 움직이는 "지도".** 처음 볼 때 학습되고, 다 훑고 나면 얼어붙는다.

이를 위해 다이어그램 구조를 흔드는 원인을 하나씩 제거한다. 실측·논증으로 확인한 구조 변화 원인은 셋뿐이며, 각각을 한 기둥으로 잡는다:

| 구조 변화 원인 | 대응 기둥 | 상태 |
|---|---|---|
| 자식이 부모 왼쪽 끝에 걸려 자식 수만큼 우측 치우침 | **① tidy-tree 중앙 정렬** | ✅ 구현(ADR-0058) |
| 공유 컴포넌트 = 다중 부모(DAG) → 순서·깊이 재계산으로 자발적 요동 | **② 공유 UI 레인** | 본 문서 설계 |
| 런타임 mount/unmount(모달·탭·라우트)로 골격 등장/소멸 | **③ 슬롯 예약(학습·동결 지도)** | 본 문서 설계 |

세 기둥을 합치면 남는 유일한 구조 변화는 **"한 번도 본 적 없는 컴포넌트의 첫 등장"** — 진짜 새 정보라, 그때 지도가 바뀌는 건 옳다.

## 0.5 간선 두 종류 — "배치=소유 / 배선=데이터" (스코프 경계)

핵심 통찰: **실제 React 렌더 트리(인스턴스 단위)는 항상 단일 부모 = 순수 트리다.** "다중 부모"는 같은 타입/파일을 그룹으로 접을 때만 생기는 아티팩트. 그래서 간선을 두 종류로 갈라야 하고, 담당이 다르다:

| 간선 종류 | 성질 | 담당 |
|---|---|---|
| **소유 간선**(부모→자식) | 순수 트리라 **항상 인접 깊이**(d→d+1), 짧다 | **배치**(tidy-tree) — 이미 깨끗, 배선 불필요 |
| **데이터 간선**(props drilling·콜백·공유 상태, ADR-0032) | 트리를 안 따름 — 깊이 건너뛰고 옆으로 점프 | **배선**(버스·평행 줄기, ADR-0054) — 배치로 못 고침 |

- 실측: 소유 트리는 이미 **교차 0**. 스크린샷에서 엉켜 보이던 라벨 달린 선(`setSelectedRestaurant`·`openAddRestaurantModal` 등)은 전부 **데이터 간선**이었다.
- **스코프 경계**(두 세션 충돌 원천 차단): 우리 레이아웃(배치)은 **소유 간선**을 책임지고 tidy-tree로 끝낸다. **데이터 간선**은 배선 세션 몫이라 안 겹친다. **유일한 예외 = 공유 컨테이너**(그룹 접기가 만든 소유-간선 엉킴) → 배치가 레인으로 국소 개입(기둥 ②).
- 사용자 설계 이력: "직속 상속(인접) vs 계층 건너뛰는 구조"를 구분하려 한 게 정확히 이 소유/데이터 구분이었다. 소유는 순수 트리라 항상 인접, 엉키는 건 건너뛰는 데이터 간선.

## 1. 기둥 ② — 공유 UI 레인

### 문제

그룹핑이 사용 위치 기준이라 대부분 단일 부모(트리)지만, **공유 컴포넌트(같은 타입이 여러 부모에서 렌더)**는 다중 부모가 된다. 이 DAG가:
- tidy-tree의 "대표 부모" 선택을 흔들고(부모 집합이 바뀌면 재선택),
- 최장경로 깊이를 다경로로 만들어 밴드를 흔들며,
- 긴 횡단 간선으로 클러터를 만든다.

즉 **자발적(코드 변화 없는) 요동의 유일한 원천이 공유 컴포넌트**다.

### 통찰 — 공유 컴포넌트는 애초에 "소유 트리"의 멤버가 아니다

`Button`은 CheckoutPanel이 소유하는 게 아니라 여러 곳이 **쓰는** 공유 자원이다. 스토어/훅은 트리 밖에서 다수에 연결된다. 단일 부모 워터풀에 억지로 넣는 게 오분류다. **빼서 별도 레인에 두면 → 남은 트리는 순수 트리(모든 노드 단일 부모)** 가 되어:
- 구조는 오직 코드 변화(mount/unmount)로만 바뀌고,
- 순수 트리의 tidy 배치는 **교차 0**(공짜).

이는 아키텍처 다이어그램의 표준(스윔레인, C4의 인프라 분리, "스토어/훅은 컴포넌트 트리와 직교")과 일치한다. **사용자 Figma 레퍼런스**(레스토랑 앱)가 정확히 이 형태였다 — 위: 데이터(json-server/QueryClient), 아래: 스토어/훅(useRestaurantStore/useModalStorage), 옆: 공유 UI(UI 폴더의 Button/Filter/Modal). 워터풀에서 벗어난 별도 구조 + 횡단 간선.

### 리프 vs 컨테이너 — 문제는 컨테이너뿐

사용 위치 그룹핑이라 공유 컴포넌트가 둘로 갈린다:

- **(A) 공유 리프**(Button·Icon, 자식 없음): `<Button/>`이 HomeHeader에 쓰이면 그 Button 노드는 **HomeHeader 그룹에 국소**로 들어간다. 5곳에 쓰면 5개의 국소 Button — 긴 선도 다중 부모도 **없음. 이미 깨끗.** → 표현은 **인라인 칩**(아래)이면 충분, 레인 불필요.
- **(B) 공유 컨테이너**(Modal·Card·Layout, 자기 서브트리 렌더): `Modal.tsx` 그룹(= Modal의 내용물)이 Aside·Header 두 곳에서 인스턴스화되면 → **`Modal.tsx` 그룹이 부모를 둘 갖는다**(다중 부모 그룹). 이 DAG가 트리를 깨고 긴 횡단 선을 낸다. → **이게 레인 대상.**

### 분류 기준 — `groupParents ≥ 2` (엔진이 이미 계산)

- 공유 컨테이너 = **부모 그룹이 ≥2개인 그룹.** 이건 엔진의 `computeGroupDepths`가 이미 반환하는 `groupParents`에 그대로 있다 — `fiber.type` 추적조차 필요 없음(더 단순).
- **거짓양성 없음**: 부모 그룹 ≥2 = 정의상 "여러 곳에서 인스턴스화됨". 임계값 N=2(순수) 또는 3(두 곳만이면 트리에 둠)로 튜닝.
- **정직한 범위**: 이 기준은 "UI"가 아니라 **재사용된 컨테이너 전부**를 잡는다 — 맞다(트리를 깨는 건 "재사용됨" 자체지 UI냐가 아님).

### 재현 검증 (2026-07-18) — 설계 전제 실증됨

지금까지 fixture는 순수 트리라 **다중 부모 그룹을 도구에서 한 번도 본 적이 없었다**(설계가 이론뿐). 그래서 먼저 재현 fixture를 추가했다: `domains/shared/Dialog.tsx`(내부 서브컴포넌트 DialogHeader/DialogBody를 렌더하는 공유 **컨테이너**)를 서로 다른 두 파일 `SettingsDialog.tsx`·`ProfileDialog.tsx`에서 쓰게 함(진입점 `SharedDialogDemo.tsx`, DemoApp에 한 줄 마운트).

- **실측 결과**: `Dialog.tsx` 그룹이 부모 2개(`SettingsDialog.tsx`, `ProfileDialog.tsx`)를 갖는 **다중 부모 그룹**으로 나타남 ✓. 공유 **리프**(`Button.tsx`)는 host만 렌더해 자기 그룹이 없어 여전히 다중 부모 안 됨 ✓ — 리프/컨테이너 구분이 실증됨.
- **현재 tidy-tree 처리**(레인 전): Dialog.tsx를 대표 부모(먼저 등장한 SettingsDialog) 아래 배치, 다른 부모(ProfileDialog)는 간선으로 연결. 즉 **설계가 겨냥한 그 구조가 이제 도구에서 재현·검증 가능**하다.
- 이로써 레인 구현 시 **before/after를 실제로 잴 수 있는 기준선**이 생겼다(과거 barycenter/no-op 상황 회피).

### 배치·표현 (구체)

**위치: 트리 아래 별도 "공유" 레인**(사용자 Figma의 스토어/훅이 바닥에 있던 것과 같은 구조). 다중 부모 그룹을 트리에서 들어내 이 밴드에 두면 **위쪽 트리는 순수 트리 = 교차 0**이 된다.

```
[지금]  App                       [레인 후]  App
       / | \                              / | \
   Aside Main Header                  Aside Main Header
     |          |                       ⌇          ⌇   ← 곡선(공유)만 아래로
  [Modal.tsx]   |  ← Modal은 Aside 밑   ┌── 공유 레인 ──────────┐
      \________/   ← Header→Modal이      │   [ Modal.tsx  ×2 ]    │
      긴 선이 트리 관통                   └───────────────────────┘
```

**표현 요소:**
- **곡선 bezier 간선** — 사용처(부모)에서 레인으로. 직교 트리 선과 구분돼 "소유 아닌 사용"이 읽힘.
- **사용 횟수 배지** — `Modal.tsx ×2`(리스트 접기와 같은 언어).
- **버스 병합** — 한 공유 노드로 들어가는 여러 선을 트렁크로(배선 세션과 co-design).
- **(선택) 사용처 인라인 칩** — 각 부모에 작은 "→Modal(공유)" 칩(Figma가 index.jsx마다 "Modal" 탭 붙인 것). 긴 선 안 따라가도 로컬에서 "여기 공유 X 씀"을 읽게. **공유 리프(Button)는 이 칩만으로 충분**(레인 불필요).

**트레이드오프(정직):** 레인 방식은 공유 선이 좀 **길어진다**(사용처→아래 레인). 대신 (a) 트리가 순수해져 안정+교차 0, (b) 선들이 라벨된 한 구역에 모여 버스로 묶임. 바닥 대신 **측면 레일**도 대안(사용 깊이가 다양하면 가로 선이 더 짧을 수 있음).

### 시각 인코딩 — 빈 채널을 골라라

의미가 다른 간선은 다른 시각 채널로. 우리는 이미:
- 실선/점선 = 같은 그룹 / 그룹 경계(ADR-0047)
- 색(hue) = 부모 도메인 / opacity = 깊이 감쇠 / 애니메이션 = props 흐름(ADR-0032)

점선·색·애니메이션은 **이미 배정**돼 겹치면 혼란. **비어있는 채널 = 기하(곡선)**:
- 트리(소유) 간선 = 지금처럼 직교/smoothstep
- **공유 사용 간선 = 곡선 bezier** → "구조를 가로질러 여러 곳에 쓰인다"가 한눈에.

그리고 **가독성의 8할은 "레인 자체"** — 별도 배경/라벨("공유")을 단 밴드면, 보는 사람이 "이 띠 = 공유, 다수 연결"을 즉시 안다. 곡선은 보강.

- **2.5D·동적 애니메이션은 유보**: 애니메이션 채널은 이미 props 흐름이 쓰고, 2.5D는 가독성 리스크 + 큰 투자(과투자 회피). 곡선+레인으로 충분한지 먼저 보고, 부족하면 실험.

### 데이터 스코프 한계 (정직하게)

우리 런타임은 **파이버 트리 = 컴포넌트**만 본다. 사용자 Figma의 훅/스토어(`useRestaurantStore`—Zustand는 컴포넌트 아님), 데이터(`QueryClient`/`json-server`)는 파이버가 아니라 **아직 못 본다**. 그래서:
- **레인 v1 = 공유 UI 컴포넌트**(다중 부모 타입)에 한정.
- 풀 비전(스토어/데이터 레인)은 **데이터 스코프 확장**(Context는 파이버라 가능, Zustand는 별도 — ADR-0032의 보류 항목) 선행.

## 2. 기둥 ③ — 슬롯 예약 (학습·동결 지도)

### 예측 불가, 기억 가능

런타임 관찰 도구라 **마운트된 적 없는 컴포넌트는 존재조차 모른다**. "앞으로 마운트될 것"을 미리 빈칸 파는 건 정적 분석(코드 파싱)이 필요하고, 그건 아키텍처 밖.

**하지만 "한 번이라도 본 것"엔 가능** — 기억으로:
- 마운트 → 언마운트돼도 **슬롯을 비운 채 유지** → 재마운트 시 원래 자리로.
- 실무 지터의 대부분이 **같은 컴포넌트의 mount/unmount 반복**(모달 열고닫기·탭·뒤로가기)이라 이걸로 대부분 잡힘.
- 프레이밍: **"앱을 쓰는 동안 지도가 학습되다가, 다 훑으면 얼어붙는다."**

### 순수 트리와의 합성

순수 트리(기둥 ②)면 각 컴포넌트의 깊이·부모가 유일하게 결정 → **슬롯 위치가 명확**. 둘을 합치면 재마운트가 항상 같은 자리로 돌아온다. → **유일한 구조 변화 = 첫 등장.**

## 3. 세 기둥 합성 결과

```
tidy-tree(중앙 정렬)  →  우측 치우침 제거, 대칭
      +
공유 UI 레인         →  DAG 제거 → 순수 트리 → 자발적 요동 0 + 교차 0
      +
슬롯 예약(학습·동결)  →  mount/unmount 요동 0 (본 것 한정)
─────────────────────────────────────────────
= 코드/새 컴포넌트 없이는 안 움직이는 골격 (개발자가 외울 수 있는 지도)
```

## 4. 미결 논의점 (구현 전 해결)

1. **ADR-0018 pruning과 정면 충돌** — ADR-0018은 언마운트 그룹을 순서에서 **지워서** 카메라 드리프트를 고쳤다. 슬롯 예약은 반대로 **유지**한다. → 재조정: 슬롯은 유지하되 카메라 refit 대상에선 빼기, 또는 "최근/자주 본 것"만 유지. 실측으로 저울질.
2. **슬롯 회수 정책** — 다 유지하면 세션이 길수록 골격이 비대·성겨진다. 후보: 부모가 살아있는 동안만 유지 / LRU / TTL / 라우트 경계 리셋. 안정 vs 밀도 트레이드오프.
3. **빈 슬롯 UI** — 그냥 빈칸이면 버그처럼 보인다. **고스트 플레이스홀더**(흐릿한 "Modal(닫힘)")로 "여기 조건부로 온다"를 표시. `group-node--collapsed`(지도 모드 접힘)와 시각 구분 필수.
4. **첫 등장 애니메이션** — 불가피한 변화지만 부모 아래 제자리에 부드럽게 삽입(order-once)해 덜 튀게.
5. **지속 범위** — 세션 한정 vs localStorage "학습된 지도"(새로고침해도 동결). 후자는 강력하나 상태·구식화 리스크.
6. **통증 검증 게이트** — 정교한 예약 시스템 전에 **실사용에서 mount/unmount 지터가 실제로 거슬리는지 실측**. 증거 없이 과투자 X(CLAUDE.md).

## 5. 배선 세션(ADR-0054)과의 조율

이 작업은 **배치/구조(안정성)** 결정이라 배선(선 그리기)이 **못 하는 일**(트리를 순수하게)을 한다. 오히려 공유 노드를 빼면 **배선 세션에 더 깨끗한 그래프**를 넘겨 돕는다 — 충돌이 아니라 상류 정리. 단:
- 공유 간선의 **곡선 스타일**은 배선 영역이라 **co-design** 필요.
- 레인 도입으로 그래프가 바뀌니, 착수 전 배선 세션과 동기화.

## 6. 지금 결정

**설계 확정, 미구현.** 구현 순서·게이트:
1. 배선 세션(ADR-0054) 안착 + 조율.
2. mount/unmount 지터 통증 실측(게이트).
3. 통과 시: 공유 UI 레인(② — multi-parent-type 식별 + 레인 + 곡선) 먼저, 그 위에 슬롯 예약(③ — 학습·동결 + 고스트).
4. 각각 ADR로 근거 남김. ADR-0018 재조정 명시.
