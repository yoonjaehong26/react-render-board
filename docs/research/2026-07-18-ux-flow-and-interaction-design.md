## 0. 읽기 전에 — 이 조사 도중 상태가 한 번 바뀌었다

이 조사를 시작한 시점과 끝낸 시점 사이에 다른 세션이 **ADR-0027**(검색 하이라이트+자동 이동, 다크모드+도메인 팔레트)을 반영했다. 이 문서는 ADR-0027 반영 **이후** 최신 워킹트리 기준으로 다시 확인해 썼다. 처음 받은 배경 설명은 "검색/다크모드는 구현됐지만 ADR 문서화는 아직"이라는 전제였는데, 지금은 그 문서화까지 끝나 있다. 그래서 이 문서의 무게중심이 착수 시점과 달라졌다:

- ~~"검색/다크모드 상태를 문서화한다"~~ → ADR-0027이 이미 했다. 대신 이 문서는 ADR-0027이 다루지 않은 **더 미세한 상호작용 조합**(검색 중 역방향 하이라이트가 겹치면? 그룹 카운트 배지는 검색을 반영하는가? 등, 2절)에 집중한다.
- 남은 미구현 항목이 하나 더 늘었다 — ADR-0027이 project-status.md에 "그룹+개별 동시 필터(도메인 통째로 숨기기)"를 검색과는 별개의 미구현 항목으로 새로 명시했다. 원래 지시받은 3항목(주석/코드점프/그룹 접기)에 참고로 덧붙인다(3.4절).
- 이 문서의 코드 인용은 전부 **작성 시점 워킹트리를 직접 읽고 확인**한 것이다(파일:라인 표기). 여러 세션이 병행 작업 중이므로(CLAUDE.md), 실제 착수 시점에 다시 확인할 것을 권한다 — 실제로 이번 조사 중 관련 코드가 한 번 바뀌는 걸 직접 목격했다.

## 2. 이미 있는 기능들의 상호작용 규칙

`project-status.md`와 ADR-0027은 각 기능이 "무엇을 하는지"는 기록했지만, 기능들이 **동시에** 걸렸을 때 무슨 일이 일어나는지는 코드에만 있고 프로즈로 문서화된 적이 없다. 아래는 `Canvas.tsx`/`toFlow.ts`/`flow.css`/`domInteraction.ts`/`main.tsx`를 직접 추적해 확인한 상태다. 표기:

- **✅ 이미 의도적으로 설계됨** — 코드가 명시적으로 처리하고, 동작이 합리적이다.
- **⚠️ 갭** — 크래시는 아니지만 아무도 설계하지 않은 시각적/논리적 충돌.
- **💡 사소한 개선 제안** — 지금 문제는 아니지만 값싸게 다듬을 수 있는 지점.

### 2.1 검색 중 지도 모드로 줌아웃하면? — ✅ 이미 설계됨

`shouldExpandGroup(frame, group)`(`Canvas.tsx:173-181`)이 그룹을 펼칠지 정하는 순서:

```
1. 이 그룹에 검색 매치나 역방향 착지 노드가 있는가? → 있으면 무조건 펼침 (최우선)
2. 지도 모드인가?                                   → 맞으면 접음
3. 뷰포트 밖인가?                                    → 맞으면 접음
4. 그 외                                            → 펼침
```

검색 매치가 지도 모드로 접힌 그룹 안에 있어도 1번이 2번보다 먼저 걸려 강제로 펼쳐지고, `fitView`가 그 노드로 카메라를 옮긴다(`search.test.ts`, `scripts/verify-search-and-theme.mjs`로 실측 검증됨).

**단, semantic zoom엔 이것과 별개인 CSS 레이어가 하나 더 있다.** `SemanticZoomController`가 전역 줌 값만으로 `.zoom-far` 클래스를 토글하고, `.zoom-far .component-node, .zoom-far .react-flow__edge { opacity: 0; pointer-events: none; }`(`flow.css:216-220`)가 모든 컴포넌트 노드를 무조건 안 보이게 한다. 두 레이어(데이터 레이어의 `shouldExpandGroup` vs CSS 레이어의 `.zoom-far`)는 서로 다른 신호에 반응하고 다른 주기로 갱신되지만(즉시 vs 200ms 디바운스), 검색 매치의 경우 결과적으로 둘 다 뚫려 있다 — `MAP_MODE_THRESHOLD`(0.55)보다 살짝이라도 안쪽으로 줌인해 있으면 매치 노드가 실제로 보인다.

**경계 조건(코드상 미처리, 기록만 남김)**: 완전히 0.55 미만까지 최대로 줌아웃한 채로 검색하면, 데이터 레이어는 그룹을 강제로 펼치지만 CSS 레이어(`.zoom-far`)는 여전히 그 노드를 `opacity:0`으로 가릴 수 있다. 실사용에서 드물지만(검색은 보통 확대해서 보려는 의도와 함께 오므로) 재현 가능한 조합이다 — 문제로 판단되면 "검색 매치가 있으면 `.zoom-far`도 해제"하는 한 줄로 고칠 수 있을 만큼 싸다.

### 2.2 검색 중에 역방향(DOM→보드) 클릭을 하면? — ⚠️ 갭 발견

확인된 사실:

- 역방향 네비게이션은 `searchQuery`를 전혀 건드리지 않는다(`Canvas.tsx:209-215`) — 검색어는 그대로 남는다.
- `highlighted`(역방향 착지)와 `matched`(검색 매치)는 `ComponentNodeData`의 완전히 독립된 두 boolean이다(`toFlow.ts:106-107`).
- 매치 안 된 노드를 흐리게 하는 규칙 `.canvas.search-active .component-node:not(.component-node--matched) { opacity: 0.25; }`(`flow.css:182-184`)은 오직 `--matched`만 예외로 둔다. `--highlighted`는 예외가 아니다.

**결과**: 검색어가 활성 상태에서, 그 검색어와 매치되지 않는 요소를 Alt+클릭(또는 픽 모드)으로 가리키면 그 노드는 `opacity: 0.25`로 흐려진 채 `rrb-highlight-pulse` box-shadow 애니메이션(`flow.css:238-254`)이 겹쳐 재생된다 — "흐릿한데 맥박치는" 노드가 된다. 크래시는 아니지만 "지금 이걸 가리키고 있다"는 강조 목적과 "덜 중요하다"는 흐림 신호가 동시에 뜨는 모순된 상태다.

**제안**: `flow.css:182`의 `:not()`에 `--highlighted`도 추가한다 — `.component-node:not(.component-node--matched):not(.component-node--highlighted)`. 기존 규칙의 의도("매치/강조 대상은 안 흐려진다")를 일관되게 넓히는 CSS 한 줄이라, 별도 설계 논의 없이 반영해도 될 만큼 작다.

### 2.3 픽 모드 중에 검색창(또는 다른 보드 UI)에 포커스가 있으면? — ✅ 이미 안전함(구조적으로)

`startDomClickBridge`의 캡처 리스너는 `subjectContainer`(`#subject-root`) **한 곳에만** 붙는다(`domInteraction.ts:85`, `main.tsx:34,47`). 보드 패널은 `document.body`에 직접 추가되는 완전히 다른 DOM 서브트리(`#board-overlay-root`, `main.tsx:49-51`)에 마운트된다. 검색창 클릭·타이핑·포커스는 전부 이 두 번째 서브트리 안에서 일어나므로, 픽 모드/Alt+클릭 리스너는 애초에 그 이벤트를 보지도 못한다 — "충돌을 처리했다"기보다 "충돌할 방법 자체가 구조적으로 없다"에 가깝다. 검색창에 포커스가 있는 채로 계측 대상 앱에서 Alt+클릭해도 정상 동작하고, 반대로 픽 모드를 켠 채 보드로 돌아와 검색창에 타이핑해도 아무 간섭이 없다.

**💡 사소한 개선 제안**: `pickModeActive`일 때 `body.rrb-pick-mode`가 `cursor: crosshair`를 `document.body` 전체에 건다(`flow.css:288-290` 부근, 서브에이전트 조사로 확인 — 직접 재검증은 안 함). 보드 패널도 `document.body`의 자손이라 커서 모양이 CSS 캐스케이드로 그대로 새어 들어간다 — 클릭해도 아무 일이 안 일어나는 검색창/툴바 위에서도 십자선 커서가 뜬다는 뜻이다. 기능 결함은 아니지만 "여기 클릭하면 뭔가 골라진다"는 잘못된 기대를 줄 수 있어, 커서 규칙을 `#subject-root`로 좁히는 스코프 조정을 제안한다.

### 2.4 필터(검색)로 좁힌 상태에서 그룹 카운트 배지는 어떻게 표시되는가? — ⚠️ 갭 발견

`GroupNodeData.count`는 `g.nodeIds.length`(`toFlow.ts:75`)로 계산된다 — 그 그룹의 **전체** 멤버 수이며 `matchedIds`를 전혀 참조하지 않는다. 즉:

- 지도 모드에서 "CheckoutItem"을 검색하면 매치를 포함한 그룹은 강제로 펼쳐지지만(2.1절), 그 프레임의 배지는 여전히 "12"(전체 멤버) 같은 원래 숫자를 보여준다 — "12개 중 몇 개가 매치인지"는 화면 어디에도 안 나온다.
- 매치가 없는 그룹은 그대로 접힌 채 배지에 전체 숫자를 보여준다 — 사용자가 좁혀서 보고 있다는 감각이 들지 않는다("검색했는데 왜 여전히 큰 박스들이 이렇게 많지?").

**제안**: 검색이 활성일 때만 배지를 `count`(전체) 대신 `matchedCount/count`(예: "3/12") 형태로 바꾼다. `toFlow`가 이미 `matchedIds`를 받고 있으므로(`ToFlowOptions.matchedIds`) 그룹별로 `g.nodeIds.filter(id => matchedIds.has(id)).length`를 한 번 더 세는 정도의 비용이다.

### 2.5 다크모드 × rough.js 스케치 테두리 — ⚠️ 갭 발견 (ADR-0027이 스코프 밖으로 남긴 항목)

`roughStyle.ts`의 `ROUGH_BORDER_COMPOSITE`/`ROUGH_BORDER_HOST`는 모듈 로드 시 한 번 계산되는 정적 SVG data-URI이고, 하드코딩된 스트로크 색(`#6366f1`/`#94a3b8`)을 쓴다 — `colorMode` 인자 자체가 이 모듈에 없다. ADR-0027도 이 스케치 테두리를 "병행 세션이 작업 중인 것을 발견"했다고만 기록했지 다크모드 대응 여부는 다루지 않았다. 결과: 다크모드로 전환해도 컴포넌트 노드의 손그림 테두리만 라이트 모드 색 그대로 남는다 — 배경 틴트·팔레트 색은 다크 대응이 되는데 이 장식 하나만 예외라 미묘하게 눈에 띌 수 있다.

**제안**: `roughStyle.ts`에서 라이트/다크 각각의 스트로크 색으로 두 세트의 data-URI를 미리 계산해(지금처럼 모듈 로드 시 1회, 개수만 2배) `colorMode`에 따라 골라 쓰게 한다 — "정적 애셋 사전 계산으로 런타임 비용 회피"(P1/ADR-0017과 같은 방향) 패턴을 유지하면서 색만 이원화하는 정도라 큰 작업이 아니다. 우선순위는 낮음(순수 미관 — 다른 항목들과 달리 기능적 혼란을 주지는 않는다).

### 2.6 픽 모드를 취소할 방법이 마땅치 않다 — 💡 사소한 개선 제안

`pickModeActive`는 (a) 토글 버튼을 다시 누르거나 (b) 아무 요소나 한 번 클릭해 성공/실패하면(`finally` 블록, `domInteraction.ts:80-82`) 자동으로 꺼진다. 버튼을 다시 누르는 것 외에 **키보드로 취소할 방법이 없다.** React Scan의 `Cmd/Ctrl+C` 단축키가 `isInputLikeFocused()`를 먼저 검사해 텍스트 입력 중엔 개입하지 않는 패턴(5절)을 참고하면, `Escape`로 픽 모드를 취소하는 단축키를 추가할 만하다 — 단, 검색창에 포커스가 있을 때 `Escape`는 (픽 모드 취소가 아니라) 검색어를 지우거나 포커스를 빼는 쪽이 사용자 기대에 더 맞을 것이다. 즉 이 단축키도 "포커스가 검색창 안에 있는가"를 먼저 검사해야 한다 — React Scan이 검증한 것과 같은 원칙.

## 3. 남은 기능 우선순위와 설계 방향

### 3.1 그룹 접기/펼치기 — 1순위 제안 (난이도 재평가)

**기존 분류를 재검토해야 하는 이유.** `react-flow-ux-capabilities.md`(ADR-0026 이전 작성)와 ADR-0027(이번 라운드) 둘 다 이 기능을 "큰 작업"으로 분류했다. 그런데 두 ADR이 이미 만들어둔 배관을 다시 보면:

- `shouldExpandGroup(frame, group): boolean` — 그룹별로 펼칠지 말지 이미 계산하고 있다(`Canvas.tsx:173-181`).
- `GroupNodeData.collapsed: boolean` — 이미 프레젠테이션 레이어까지 내려와 있고 `GroupNode.tsx:18`이 이미 `group-node--collapsed` 클래스로 소비한다.
- `toFlow`는 `expanded`가 `false`인 그룹의 자식 노드/엣지를 **아예 배열에 안 넣는다**(`toFlow.ts:85`, `if (!expanded) continue;`) — "접기"가 요구하는 정확한 동작(자식을 숨기는 게 아니라 안 만드는 것, ADR-0016/0017의 뷰포트 최적화와 같은 이득)을 이미 공짜로 얻는다.

즉 이 기능이 필요로 하는 핵심 메커니즘은 전부 이미 있다 — 없는 건 **트리거할 세 번째 입력**(지금은 검색 매치/역방향 착지/지도 모드/뷰포트, 이 네 가지뿐)과 **클릭 UI**뿐이다. 구체적으로:

```
function shouldExpandGroup(frame, group) {
  if (group === highlightedGroup || matchedGroups.has(group)) return true;  // 기존 — 최우선
  if (manuallyCollapsed.has(group)) return false;                          // 신규 — 검색/하이라이트 다음
  if (isMapMode) return false;                                             // 기존
  if (!viewRect) return true;                                              // 기존
  return rectsIntersect(frame, viewRect);                                  // 기존
}
```

**우선순위 규칙(제안)**: 검색 매치/역방향 착지 > 수동 접기 > 지도 모드 > 뷰포트 컬링. 근거: 검색은 `ui-philosophy.md`가 명시한 "탈출구"라 다른 모든 것보다 이겨야 사용자가 "분명히 찾았는데 왜 안 보이지"에 빠지지 않는다. 반대로 수동 접기는 사용자의 명시적 의도이므로 자동 규칙(지도 모드/뷰포트)보다는 이겨야 한다 — 안 그러면 "접었는데 확대하니 다시 펼쳐지네"가 매번 반복돼 수동 조작의 의미가 없어진다.

**주의할 경계 조건**: 수동 "펼침" 상태는 **지도 모드 전역 줌 임계값과는 다른 축**이다. `SemanticZoomController`의 `.zoom-far` CSS 규칙(2.1절)은 그룹 단위가 아니라 전역 줌 값 하나로 모든 컴포넌트 노드를 가린다 — 그룹 하나를 수동으로 "펼침" 상태로 만들어도, 화면이 전역적으로 지도 모드 임계값 아래면 그 안의 내용은 여전히 안 보인다(데이터 레이어엔 존재하지만 CSS 레이어가 가린다). 버그가 아니라 지도 모드의 정의 그대로지만, 구현 중 "왜 펼쳤는데 안 보이지"로 헷갈리기 쉬우니 미리 적어 둔다 — 수동 접기/펼치기는 **상세 모드로 줌인했을 때부터 의미가 생기는 기능**으로 소개하는 게 맞다.

**UI 어포던스**: `.group-node__header`(이미 존재, `GroupNode.tsx:28`)에 작은 chevron 버튼을 추가하는 걸 제안한다. 프레임 전체를 클릭 대상으로 삼지 않는 이유: 그룹 프레임 안의 노드를 클릭하려다 실수로 그룹째 접히는 사고를 줄이기 위해서다. `onNodeClick`(`Canvas.tsx:256-264`)은 지금 `node.type !== 'component'`이면 조기 리턴하는데, 이건 ADR-0024 결정 5("그룹 프레임 클릭 시 DOM 하이라이트는 하지 않는다")의 구현이지 "그룹 클릭에 어떤 동작도 절대 안 된다"는 금지가 아니다 — `node.type === 'group'`일 때 별도로 접기 토글을 처리하는 분기를 추가해도 ADR-0024와 충돌하지 않는다.

**3.4절과의 관계**: "그룹+개별 hidden 필터"(도메인 통째로 숨기기)는 이 기능과 배관이 겹친다 — 둘 다 "그 그룹의 자식을 flowNodes에서 뺀다"는 동일한 동작이고 차이는 트리거뿐이다(검색 매치 여부 vs 사용자가 명시적으로 끈 도메인). 그룹 접기를 먼저 만들면 hidden 필터는 그 배열-제외 로직을 재사용해 훨씬 싸게 뒤따라올 수 있다.

### 3.2 캔버스 주석(스티키노트) — 2순위 제안

`react-flow-ux-capabilities.md`(§3-B)가 이미 "선행 조건 없음, 간단~중간"으로 분류했고 이번 조사로도 그 판단은 유효하다. 다만 이 프로젝트만의 제약 하나를 짚어야 한다:

**공식 예제(Save and Restore, `toObject()`+`localStorage`)를 그대로 못 쓴다.** 그 예제는 "사용자가 편집한 정적 그래프"를 전제로 `nodes`/`edges` 배열 전체를 저장·복원한다. 이 프로젝트의 `flowNodes`는 매 커밋 `useMemo`로 **라이브 스냅샷에서 통째로 다시 계산**된다(`Canvas.tsx:144-197`) — 주석을 그 배열 안에 직접 넣으면 다음 리렌더에서 사라진다. 이미 확립된 패턴(검색의 로컬 `searchQuery`, 역방향의 `interactionStore`)과 같은 방식으로 풀어야 한다:

- 새 `annotationStore.ts`(`interactionStore.ts`와 같은 `subscribe/getSnapshot` 패턴) — `{id, x, y, text}[]`를 들고 `localStorage`에 영속화(`colorModePreference.ts`가 이미 쓰는 패턴 재사용).
- `Canvas.tsx`의 `flowNodes` 조립부가 이 스토어의 항목들을 `type: 'annotation'`인 별도 노드로 배열 끝에 얹는다 — 컴포넌트/그룹 노드와 같은 배열에 섞이지만 데이터 소스와 갱신 주기가 다르다는 걸 명확히 분리한다.

**세부 주의점(기존 조사 재확인)**: 텍스트 영역엔 React Flow 공식 `nodrag`/`nopan` 클래스가 필요하다(자동 적용 안 됨). 그룹 접기(3.1절)와의 관계: 주석을 그룹 프레임 안에 놓을 수 있게 할지(도메인에 딸린 메모) 여부는 스코프를 넓힐 여지지만, **1차 스코프는 그룹에 안 묶인 자유 배치 메모만으로 좁히길 제안**한다 — 그룹의 자식으로 만들면 `extent:'parent'`/좌표계 문제가 늘고, "이 도메인에 대한 메모"라는 요구가 실제로 나온 적은 아직 없다(CLAUDE.md의 과잉 설계 금지 원칙과 같은 방향).

### 3.3 컴포넌트 코드로 점프 — 3순위 제안 (2단계로 쪼개기)

**선행 작업(스키마 확장)은 이미 정확히 스코프됐다.** `sourceHints.ts:17`에서 `getSource(fiber)`가 돌려주는 `{fileName, lineNumber, columnNumber}` 중 `fileName`만 `sourceHints.ts:18`에서 남기고 나머지는 버린다. 확장 지점은 정확히 세 곳이다: ① `GroupHintResult`(`sourceHints.ts:7-10`)에 필드 추가, ② 같은 파일 17-18행에서 버리지 않고 채우기, ③ `RenderNode`(`src/data/types.ts:5-16`)와 `store.ts`의 `hintCache`(현재 `Map<number, string|null>`)에 필드 반영. 데이터 스키마 변경이지만 architecture.md가 말하는 "되돌리기 어려운 결정"의 무게는 아니다 — 필드 추가이지 기존 필드 의미 변경이 아니다.

**점프 메커니즘은 두 단계로 나누길 제안한다** — 기존 조사(react-flow-ux-capabilities.md §4)가 확인한 신뢰성 문제 때문이다:

1. **1단계(먼저 만들 것): 클립보드로 경로 복사.** `file:line:col` 문자열을 만들어 복사 버튼 하나로 끝난다 — 딥링크의 이중 확인창(`vscode://`, VS Code 자체 확인창까지 2중, [issue #95670](https://github.com/microsoft/vscode/issues/95670) 미해결)도, 번들러 종속(Vite `launch-editor` 미들웨어는 Vite 전용)도 없다. 사용자가 에디터의 "파일로 이동"(Cmd/Ctrl+P류)에 붙여넣으면 되므로 에디터 무관이다 — 이 프로젝트가 이미 ADR-0021에서 검증해 둔 번들러 무관성(Vite/webpack/Rspack/Turbopack) 방향과도 맞는다.
2. **2단계(나중, 선택적): `vscode://` 딥링크.** 신뢰성 문제(이중 확인창, 성공 여부를 감지할 방법이 없는 fire-and-forget)를 사용자에게 알리는 선에서 "시도해보기" 버튼 정도로 추가할 수 있다. `launch-editor` 미들웨어 방식(더 신뢰할 수 있음)은 **권장하지 않는다** — Vite 전용 커스텀 플러그인이 필요해, 이 프로젝트가 배포 UX에서 이미 정한 번들러 무관 목표(ADR-0021)와 어긋난다.

**UI 표면**: 지금 이 프로젝트엔 "노드를 선택하면 뜨는 부가 정보 패널" 같은 게 전혀 없다(클릭은 전부 DOM 하이라이트 정방향 인터랙션에 쓰인다). 공식 `NodeToolbar`(React Flow 예제, `reactflow.dev/examples/nodes/node-toolbar`)를 얹는 걸 제안한다 — 컴포넌트 노드는 그룹 노드와 달리 `selectable:false`가 안 걸려 있어(`toFlow.ts`의 컴포넌트 노드 push 블록, 93-110행엔 이 필드가 없음 — 그룹 push 블록 80-81행에만 있음) 이미 React Flow 기본 선택 상태를 갖고 있다. 선택된 노드 위에 툴바를 띄우는 건 새 상태 배선 없이 바로 붙는다는 뜻이다. 이 위치는 5절에서 다루는 "기능이 늘어나면 전역 툴바가 아니라 아이템별 진입점으로 옮겨야 한다"는 사례 조사와도 일치한다 — 나중에 코드 보기 버튼을 하나 더 놓을 자리도 자연스럽게 마련된다.

### 3.4 (참고) 그룹+개별 hidden 필터 — 우선순위 경쟁 대상 아님, 그룹 접기 직후 권장

ADR-0027이 project-status.md에 새로 명시한 항목이다(이 조사 착수 시점엔 없던 정보). 검색 하이라이트(흐림)와는 다른 기능 — 도메인 자체를 안 보이게 완전히 배열에서 뺀다. 3.1절에서 지적했듯 이 기능이 필요로 하는 배관(그룹별로 flowNodes 배열에서 자식을 빼는 것)은 그룹 접기와 사실상 같다. 원래 지시받은 3항목(주석/코드점프/그룹접기)과 나란히 경쟁하는 4번째 우선순위로 다루기보다, **그룹 접기 작업 안에서 자연스럽게 같이 검토**하길 제안한다(같은 라운드일 필요는 없지만, 순서상 그룹 접기 다음 자리).

### 3.5 종합 우선순위

| 순위 | 기능 | 난이도(재평가) | 근거 |
|---|---|---|---|
| 1 | 그룹 접기/펼치기(수동) | 중간(기존 배관 재사용) | 이미 측정된 P2 잔여 한계(ADR-0018)를 사용자가 직접 완화하는 탈출구. 배관 대부분 존재 |
| 2 | 캔버스 주석(자유 배치, 로컬 저장) | 간단~중간 | 선행 조건 없음, 온보딩/1인 사용 시나리오에 바로 값 |
| 3 | 코드로 점프 (1단계: 클립보드 복사만) | 간단(스키마 확장 포함) | 선행 스키마 작업 3곳으로 스코프 확정. 2단계(딥링크)는 이후 별도 판단 |
| (참고) | 그룹+개별 hidden 필터 | 그룹 접기에 곁들임 | 배관 공유, 독자 우선순위 아님 |

1·2순위는 서로 독립적이라(다른 파일, 다른 상태) 병렬 진행도 무방하다 — 순서를 지킬 필요가 있는 건 3순위뿐(스키마 확장이 점프 UI보다 먼저여야 함).

## 4. 온보딩 여정 — 처음 켠 사람이 무엇을, 어떤 순서로 발견하는가

### 4.1 지금 실제로 벌어지는 순서 (코드로 확인)

1. **첫 화면**: 계측 대상 앱이 전체 화면(`main.tsx:24-31`). 보드는 안 보인다 — `boardOpen: false`가 초기값이고, 패널 DOM 자체가 `boardOpen`이 `true`가 되기 전까진 만들어지지도 않는다(CSS로 숨긴 게 아니라 존재하지 않음).
2. **유일한 첫 진입 신호**: 우하단 플로팅 버튼. 키보드 단축키도, 자동으로 열리는 경로도 없다.
3. **버튼을 누르면**: 화면 하단 45vh 도킹 패널이 열리며 라이브 렌더 트리가 즉시 보인다 — 계측 대상 앱은 위쪽에 그대로 남아 계속 조작 가능하다(ADR-0025의 핵심 목적).
4. **패널 안에서 처음 보이는 것**: 항상 켜져 있는 툴바(host 노드 체크박스, 검색창, 다크모드 토글, 커밋/노드 카운터) + 그 아래 캔버스(그룹 프레임 + 컴포넌트 노드).
5. **자연스럽게 발견되는 것**: 마우스 휠로 줌 아웃/인 → 지도 모드/상세 모드 전환. React Flow의 기본 조작(휠 줌, 드래그 팬)이라 별도 학습 없이 우연히도 만나게 된다.
6. **의도적으로 시도해야 발견되는 것**: 컴포넌트 노드를 클릭 → 실제 화면 요소가 잠깐 하이라이트(정방향). 검색창 타이핑(늘 보이는 UI라 발견 자체는 쉽지만 "이게 뭘 하는지"는 써봐야 안다).
7. **가장 발견하기 어려운 것**: 역방향(계측 대상 앱에서 Alt+클릭, 또는 "🎯 요소 선택" 버튼). 유일한 설명은 그 버튼의 `title` 툴팁뿐(호버해야 보임, 터치 기기에선 사실상 안 보임) — Alt+클릭이라는 대안 제스처를 알려주는 문구는 그 툴팁 하나뿐이다.

### 4.2 발견된 갭

- **온보딩 설명이 데모 전용이다.** `main.tsx:25-29`의 안내 배너("우측 하단 버튼을 눌러…")는 이 저장소의 데모 하네스에만 있고, `src/index.ts`가 실제로 공개 export하는 `BoardOverlay`/`Canvas`엔 없다. 이 프로젝트가 언젠가 서드파티 앱에 npm으로 설치돼 쓰인다면(ADR-0020의 최종 목표), 그 사용자는 이 배너를 절대 못 본다 — 지금 온보딩 경험의 전부가 데모에서만 재현된다.
- **빈 상태 메시지가 없다.** 계측된 컴포넌트가 0개인 상황(계측 대상 앱이 아직 안 마운트됐거나, 코드 스플리팅 로딩 중이거나)에서 툴바 카운터는 그냥 "0 / 0 노드 표시 중"이라고만 뜬다 — Redux DevTools의 "스토어를 찾을 수 없음. 안내를 따르세요" 같은 명시적 안내가 없다(5절).
- **역방향 인터랙션의 발견성이 낮다.** 어느 정도 의도된 트레이드오프이기도 하다 — React DevTools 엘리먼트 피커도 Redux DevTools도 "브라우저 확장/개발자 도구"라는 익숙한 맥락 안에 있어 설명이 거의 필요 없지만, 이 프로젝트는 도킹 패널이라는 새로운 셸이라 설명 없이 발견되긴 어렵다.

### 4.3 제안 — 가볍게, 새 인프라 없이

CLAUDE.md의 "과한 도구/프로세스 투자 금지" 원칙에 맞춰, 이미 쓰고 있는 패턴(작은 유틸 + `localStorage` 1키)만 재사용하는 선에서 제안한다 — 새 라이브러리·튜토리얼 엔진·애니메이션 워크플로 없음:

1. **1회성 힌트 배너**: `colorModePreference.ts`와 같은 모양의 유틸(`localStorage` 키 하나, 예: `rrb:onboarding-seen`)로 "처음 보드를 여는 순간"에만 패널 안에 짧은 배너(정방향/역방향 인터랙션 한두 문장 + 닫기)를 띄우고, 닫으면 다시 안 뜬다. `BoardOverlay.tsx` 안에 넣으면 데모뿐 아니라 실제 배포본에도 자동으로 따라간다 — 지금 데모 전용인 안내 문구를 재사용 가능한 컴포넌트로 옮기는 효과도 겸한다.
2. **빈 상태 메시지**: `visibleCount === 0 && totalCount === 0`일 때 캔버스 자리에 "계측된 컴포넌트가 없습니다 — 계측 대상 앱이 마운트됐는지 확인하세요" 같은 안내로 교체(Redux DevTools 패턴, 5절). 새 상태 없이 이미 계산되는 두 카운터 값만 검사하면 된다.
3. **픽 모드 버튼의 라벨/툴팁은 이미 충분히 좋다** — 아이콘(🎯)+명확한 라벨+툴팁 조합은 그대로 두고, 1번 배너에 "Alt+클릭도 됩니다"를 한 번 더 노출하는 정도로 보강한다.

## 5. 유사 devtools의 UI 배치 사례

TanStack Query Devtools · Redux DevTools · React Scan 세 도구를 "여러 기능을 어떤 UI 배치로 노출하는가"에 초점을 맞춰 조사했다(내부 구현이 아니라 배치 패턴만).

**TanStack Query Devtools** — 플로팅 토글 버튼(이 프로젝트가 ADR-0020에서 이미 참고한 선례)으로 열리는 단일 패널. 안에서는 탭이나 커맨드 팔레트가 아니라 **"늘 보이는 필터/정렬 행" + "항목을 클릭해야 나오는 상세 패널"**로 나뉜다. 테마·도킹 위치 같은 도구 전체 설정은 별도 gear 메뉴로 빠져 있다 — 콘텐츠별 액션(항목 조회)과 도구 전체 설정(테마 등)을 같은 툴바에 안 섞는다는 게 핵심 시사점이다. ([공식 문서](https://tanstack.com/query/latest/docs/framework/react/devtools), [소스](https://github.com/TanStack/query/blob/main/packages/query-devtools/src/Devtools.tsx))

**Redux DevTools** — 액션 리스트 + 스왑 가능한 "모니터"(Inspector가 기본, Chart/Trace/Test는 별도 탭) 구조. 필터는 라이브 검색창이 아니라 allowlist/denylist 설정(구식이지만, 이 프로젝트의 실시간 substring 검색이 상대적으로 더 현대적인 선택이었음을 방증한다). 스토어 감지 전 "No store found. Make sure to follow the instructions."라는 구체적 빈 상태 문구가 여러 이슈에서 반복 확인된다(4.3절 제안의 직접 근거). ([features 설정](https://github.com/reduxjs/redux-devtools/blob/main/extension/docs/API/Arguments.md), [빈 상태 사례 #547](https://github.com/zalmoxisus/redux-devtools-extension/issues/547))

**React Scan** — 클릭해서 여는 단계 자체가 없다(기본으로 자동 삽입되는 툴바). 왼쪽부터 "요소 검사"(픽 모드, 아이콘 스왑) · "알림"(팝오버) · "리렌더 아웃라인"(항상 켜짐) 버튼이 나란히 놓인다 — 이 프로젝트의 "🎯 요소 선택" 버튼과 정확히 같은 모델이라, 현재 선택이 업계 패턴과 일치함을 확인해준다. 검색 기능 자체는 없지만, 유일한 전역 단축키(Cmd/Ctrl+C, "요소 복사")가 `isInputLikeFocused() || hasNonEmptyTextSelection()`을 먼저 검사해 텍스트 입력 중엔 얌전히 물러난다 — 2.6절이 제안한 `Escape` 단축키 가드에 그대로 옮겨올 수 있는, 소스로 확인된 패턴이다. ([toolbar 소스](https://github.com/aidenybai/react-scan/blob/main/packages/scan/src/web/views/toolbar/index.tsx), [Cmd/Ctrl+C 가드](https://github.com/aidenybai/react-scan/blob/main/packages/scan/src/web/widget/header.tsx))

**세 사례가 3절의 배치 결정에 주는 시사점**:

| 신규 기능 | 배치 제안 | 근거 사례 |
|---|---|---|
| 그룹 접기/펼치기 | 그룹 프레임 자체의 chevron(아이템별 진입점) | TanStack의 "항목 클릭 → 상세/액션", React Flow 공식 컨텍스트 메뉴 예제 |
| 캔버스 주석 | 툴바 버튼으로 "추가 모드" 진입(전역 토글) | React Scan의 "Inspect" 버튼이 모드를 무장(arm)하는 패턴 |
| 코드로 점프 | 선택된 노드 위 `NodeToolbar`(아이템별) | Redux DevTools의 항목별 아이콘 액션(jump/skip/pin) |
| (장기) 도구 전체 설정이 늘어나면 | 툴바에 계속 얹지 말고 별도 gear 메뉴로 분리 | TanStack의 설정-vs-콘텐츠 분리 |

공통 원칙: **콘텐츠에 대한 액션(그룹 접기, 코드 보기)은 그 아이템 옆에, 도구 전체에 대한 설정(테마 등)은 전역 툴바에.** 지금 이 프로젝트의 툴바(host 토글, 검색, 테마)는 전부 "도구 전체" 카테고리라 이 원칙과 이미 일치한다 — 관건은 새로 추가할 기능들을 습관적으로 같은 전역 툴바에 얹지 않는 것이다.

## 6. 종합 제안 — 다음 액션

1. 2절의 갭 중 2.2(CSS 1줄)·2.4(matchedCount 배지)는 크기가 작아 별도 설계 논의 없이 반영해도 될 정도다 — 다만 사용자 확인 후 진행.
2. 3.1(그룹 접기)을 다음 UX 라운드 1순위로, 3.2(캔버스 주석)를 병렬 가능한 2순위로 제안한다. 착수 시 이 문서의 `shouldExpandGroup` 확장 스케치를 출발점으로 삼되, 실제 코드는 착수 시점 워킹트리를 다시 읽고 확인할 것 — 이번 조사 중에도 병행 세션이 관련 코드를 바꾸는 걸 실제로 목격했다.
3. 3.3(코드 점프)은 스키마 확장(3곳)부터 먼저 끝내고, 클립보드 복사 UI만 1차로 붙이는 걸 제안한다 — 딥링크는 별도 판단.
4. 4.3의 온보딩 배너/빈 상태 메시지는 위 우선순위와 별도로, 비용이 작으니 아무 때나 끼워 넣기 좋다.
5. 채택되는 항목은 다음 빈 ADR 번호로 문서화한다 — 이 문서 작성 시점 기준 **0028**이지만, 실제 착수 시 `docs/decisions/README.md`를 다시 확인할 것(이번 조사 진행 중에도 0027이 새로 채워지는 걸 목격했다).
6. 이 문서를 `project-status.md`의 "관련 문서" 목록에 링크할지는 원 채팅에서 결정한 뒤 반영하는 걸 제안한다 — 지금은 결정 전 제안 단계라 이 문서 밖의 다른 문서는 건드리지 않았다.
