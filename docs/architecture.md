# Architecture

## 동작 원리

react-render-board는 **소스 코드를 파싱하지 않는다.** 대신 브라우저에서 실행 중인 React 앱이 이미 메모리에 만들어 둔 Fiber 트리를 실시간으로 읽는다.

핵심 메커니즘:

1. React는 개발 모드에서 실행되면 `window.__REACT_DEVTOOLS_GLOBAL_HOOK__`이라는 전역 객체를 심는다. 원래 React DevTools가 쓰라고 만들어 둔 공식 통로다.
2. 이 훅에 커스텀 핸들러를 붙이면(monkey-patch), 컴포넌트가 커밋될 때마다(=렌더될 때마다) 그 순간의 Fiber 트리, props, state, context를 가로챌 수 있다.
3. 가로챈 데이터를 정규화된 스키마로 변환한다.
4. 그 데이터를 시각화 레이어에 넘겨 박스+선 다이어그램으로 그린다.

이 방식이 "실시간"이 가능한 이유이자, 동시에 **React 내부 구조가 버전마다 바뀌면 훅킹 코드가 깨지기 쉬운 이유**이기도 하다. 그래서 훅킹 레이어는 직접 구현하지 않고 검증된 라이브러리에 위임한다.

## 3-레이어 구조

프로젝트를 세 겹으로 분리해서 생각한다. 이 분리가 선행 프로젝트들이 죽은 지점을 피하는 핵심이다.

### 1. 훅킹 / 백엔드 레이어 (직접 구현 안 함)

Fiber 트리 접근과 안전한 훅킹은 검증된 라이브러리에 위임한다. 후보:

- **bippy** — react-scan 제작자가 만든 툴킷. `instrument()`, `secure()`로 안전한 패치 + try/catch 래핑을 제공. 가볍고(~4kb) 최신 React(v17–19) 특화. 활발히 관리됨.
- **react-devtools-core** — Meta 공식 유지보수. 더 보수적/안정적. Manifest V3 대응 완료.

비교와 최종 선택 근거는 [`decisions/0002-hooking-layer.md`](decisions/0002-hooking-layer.md) 참고.

이 레이어를 직접 짜지 않는 것이 로드맵의 핵심 원칙이다. 선행 프로젝트들이 가장 복잡하고 자주 깨진 부분이 바로 이 "render 함수 직접 몽키패칭"이었기 때문이다.

### 2. 데이터 레이어

훅킹 레이어가 뽑아준 Fiber 트리를 **정규화된 스키마**로 변환한다. 이 스키마는 시각화 레이어 전체가 의존하는 기반이므로, **되돌리기 어려운 결정**이다. MVP 단계에서도 신중하게 정한다.

스키마에 담을 것 (초안):

- 노드: id, displayName, 타입(host/composite), 부모 id
- 그룹핑 힌트: 소스 파일 경로 또는 도메인 (클러스터링용)
- (선택) props/state 요약, 렌더 타이밍

### 3. 시각화 레이어 (직접 구현하는 핵심 부분)

정규화된 데이터를 박스+선 캔버스로 그린다. **React Flow (xyflow)** 기반으로 구현한다. 드래그 가능한 노드, 커스텀 엣지, 줌/팬이 내장돼 있어 레이아웃 엔진을 새로 짤 필요가 없다.

선행 프로젝트들은 전부 D3를 로우레벨로 직접 다뤘는데, React Flow를 쓰면 "무엇을 노드로 보여줄지"에만 집중할 수 있다.

기존 프로젝트들(React-Sight, Realize 등, 모두 MIT)의 D3 레이아웃 코드는 **참고 자료**로만 활용한다. fork해서 위에 얹는 것이 아니라 "이렇게 접근했구나" 하는 레퍼런스로 본다.

## "fork냐 처음부터냐"에 대한 입장

엄밀히는 둘 다 아니다. 정확한 표현은:

> **공식 devtools 기반(1레이어)을 그대로 쓰고, 시각화 부분(3레이어)만 새로 쓴다.**

훅킹 로직은 물려받을 이유가 없고(어차피 위임), Manifest V2 구조는 이미 지원 종료라 새로 짜야 하며, 물려받을 가치가 있는 D3 시각화는 React 버전과 무관해 참고만 하면 된다. 결과적으로 코드량은 "처음부터"에 가깝게 느껴진다.
