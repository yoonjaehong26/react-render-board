# ADR-0017: P1 — Canvas 파이프라인의 뷰포트 기반 부분 재계산

- 상태: 채택됨
- 날짜: 2026-07-17

## 맥락

ADR-0012/0013/0014가 공통으로 도달한 결론 — "인터랙션 응답 배율이 노드 수에 초선형으로 나빠지고, 디바운스(ADR-0012)는 재계산 *빈도*만 줄일 뿐 *1회 비용*은 못 줄인다" — 을 해소한다. 세 ADR 모두 "뷰포트 기반 부분 재계산"을 다음 단계로 지목했지만, **어느 하위 단계(`normalizeForCanvas`/`toFlow`/레이아웃 엔진/React Flow 재조정)가 실제 병목인지는 프로파일링 없이 추정만 했다**(ADR-0014). 이번 ADR은 먼저 실측으로 병목을 특정한 뒤, 그 결과에 맞춰 구현 방향을 정한다.

## 프로파일링

`Canvas.tsx`의 `useMemo`에 `performance.mark`/`performance.measure`를 임시로 삽입하고, `?stressCount=2000` 상태에서 Counter 버튼을 연타하며 React 19의 자동 컴포넌트 렌더 트레이싱(Performance 타임라인에 컴포넌트별 `measure` 항목을 남기는 기능)과 함께 관찰했다(`scripts/verify-stress-scale-live.mjs`가 쓰는 것과 같은 라이브 훅킹 파이프라인, 별도의 임시 계측 스크립트 — 프로파일링 종료 후 계측 코드는 제거하고 실제 코드에는 남기지 않았다).

| 단계 | 소요(중앙값) |
|---|---|
| `normalizeForCanvas` | 1.1ms |
| `toFlow`(레이아웃 엔진 `computeLayout` 포함) | 1.4ms |
| 실제 `ComponentNode`/`GroupNode` React 컴포넌트 렌더 | 211개 렌더, 각 0.1ms(= `onlyRenderVisibleElements`가 의도대로 화면 밖은 실제 렌더를 건너뜀) |
| 커밋 시작 → 다음 페인트("commit-to-paint") | **413.3ms** |

**병목은 `normalizeForCanvas`/`toFlow`가 아니었다** — 5,000노드 규모에서도 둘 다 수 ms에 불과했다(ADR-0014의 exp2 `computeLayout` 실측 0.6~7.5ms와 일치). 진짜 비용은 "commit-to-paint" 구간에 있었고, 그 안에서 `NodeComponentWrapperInner`(React Flow가 `nodes` 배열의 **모든** 원소마다 만드는 내부 wrapper 컴포넌트)가 6번의 클릭 동안 **14,838번** 렌더됐다 — 실제로 화면에 그려진 `ComponentNode`는 211개뿐인데도. 즉 **`onlyRenderVisibleElements`(ADR-0009 ③)는 "화면 밖 노드의 실제 DOM 렌더"만 건너뛸 뿐, React Flow가 `nodes` 배열 크기만큼 치르는 내부 wrapper 처리 비용(부모-자식 절대좌표 계산, 내부 룩업 재구축 등)은 건너뛰지 못한다.** 이 비용은 "몇 개가 화면에 보이는가"가 아니라 "`nodes` 배열에 원소가 몇 개인가"에 비례한다 — ADR-0014가 몰랐던 정확한 병목 지점이다.

## 검토한 대안

- **(a) `normalizeForCanvas`/`toFlow`를 더 잘게 메모이즈한다** — 기각. 이미 병목이 아닌 곳을 더 최적화해봤자 효과가 없다는 게 프로파일링으로 확인됐다.
- **(b) React Flow를 다른 라이브러리로 교체한다** — 스코프 밖. architecture.md가 명시적으로 내린 결정이고, 프로파일링 결과 문제는 "React Flow 자체"가 아니라 "우리가 얼마나 큰 `nodes` 배열을 넘기는가"이므로 교체 없이 해결 가능하다고 판단했다.
- **(c) 뷰포트에 실제로 보이는 그룹만 `toFlow`가 개별 컴포넌트 노드/엣지 객체를 만들어 `flowNodes`/`flowEdges` 배열에 넣고, 화면 밖 그룹은 프레임(라벨+개수)만 넣는다 — React Flow에 넘기는 배열 자체의 크기를 줄인다** — 채택.
- **Rust/WASM 도입** — 이번 스코프에 포함하지 않음(사용자 지시). 순수 연산(`computeLayout`)은 프로파일링으로도 병목이 아님이 재확인됐고, 실제 병목(React Flow의 배열 크기 비례 내부 처리)은 WASM으로 해결되지 않는 JS/DOM 레이어의 문제다.

## 결정

### 1. 그룹 단위 뷰포트 컬링 (`src/visualization/lib/toFlow.ts`, `src/visualization/Canvas.tsx`)

`toFlow`에 `shouldExpandGroup(frame, group)` 콜백을 추가했다. 그룹 프레임 노드는 **항상** 만들지만(라벨+개수는 화면에 안 보여도 정확해야 한다), `shouldExpandGroup`이 `false`를 반환하면 그 그룹의 자식 `ComponentNode`/엣지는 아예 만들지 않는다 — 화면 밖 그룹은 `normalizeForCanvas`가 골라낸 전체 노드 목록과 무관하게 React Flow의 `nodes`/`edges` 배열에서 완전히 빠진다.

`Canvas.tsx`(`BoardContent`, `ReactFlowProvider` 안으로 분리)가 매 커밋마다 `shouldExpandGroup`을 계산한다:
- 지도 모드(줌 < `MAP_MODE_THRESHOLD`, `SemanticZoomController`와 공유하는 상수)에서는 뷰포트와 무관하게 전부 접는다 — 개별 노드가 애초에 안 보이므로(semantic zoom) 만들 이유가 없다. P2(다음 ADR)의 LOD와 같은 방향.
- 상세 모드에서는 그룹 프레임이 "안정된(settled) 뷰포트"(패닝/줌 여유 50% 마진 포함)와 교차하는지로 판단한다.

**"안정된 뷰포트"**는 `useViewport()`의 실시간 값을 그대로 쓰지 않고, 마지막 변화 후 200ms 지나야 반영되는 `useSettledViewport`를 거친다 — 드래그 도중 매 프레임 재계산하면 이 최적화 자체가 무의미해지기 때문이다(ADR-0009/0012의 커밋 디바운스와 같은 판단).

### 2. 엣지도 "펼쳐진 두 끝점이 모두 존재할 때만" 생성

`toFlow`가 만든 `expandedIds` 집합을 기준으로, 부모·자식 둘 다 펼쳐진 그룹에 속할 때만 엣지를 만든다 — 한쪽이 접힌 그룹에 속하면 그 엣지는 애초에 화면에 그릴 대상이 없다.

## 근거

`scripts/verify-stress-scale-live.mjs`(646/1,000/2,000/5,000, `REPEATS=3`, Counter 10회 클릭 중앙값, board on/off 배율)로 검증했다. P0(ADR-0016) 수정으로 노드 수 기준선이 바뀌었으므로, "수정 전" 값도 P0 적용 이후·P1 적용 이전 상태로 재측정했다.

## 결과

**수정 전/후 배율 비교 (board 열림/닫힘, Counter 10회 클릭, `REPEATS=3` 중앙값)**

| 스트레스 규모(총 노드 수) | P0만 적용(수정 전) | P0+P1 적용(수정 후) |
|---|---|---|
| 0(~120) | 1.17배 | 1.14배 |
| 646(~2,106) | — | **1.00배** |
| 1,000(~2,848) | — | **0.96배** |
| 2,000(~4,968) | **11.69배** | **1.05배** |
| 5,000(~10,968) | **28.32배** | **1.26배** |

응답 배율이 **노드 수와 무관하게 1배 안팎으로 평탄해졌다** — 초선형 악화가 사실상 사라졌다.

**실제 앱(shadcn-admin, `/users?pageSize=100`, 9,818개 노드) 교차 확인**

| 지표 | P0만 적용 | P0+P1 적용 |
|---|---|---|
| 오버레이 열림/닫힘 배율(검색어 5글자 입력) | 1.41배 | **0.70배**(오차 범위 내 사실상 무차이) |
| host 노드 포함 토글 반영 시간 | 3,358ms | **906ms** |

**예상 밖 발견 — ADR-0013(고빈도 렌더 스트레스)의 문제도 부수적으로 완전히 해소됐다.** 이번 ADR은 "정적으로 큰 트리"만 겨냥했는데, `scripts/verify-high-frequency.mjs`(stepwise, `SKIP_MEMORY_SOAK=1`)로 재확인한 결과 60Hz(기존 3.85배) → **1.01배**, 240Hz(기존 6.44배) → **0.96배**로, 전 Hz 구간(0/10/30/60/120/240)이 0.96~1.08배 범위로 평탄해졌다. 두 ADR이 서로 다른 스트레스 축("몇 개 노드인가" vs "몇 Hz로 갱신되는가")을 다뤘지만 근본 병목(React Flow에 넘기는 배열 크기)이 같았기 때문으로 보인다 — 별도 수정 없이 함께 해결됐다.

## 알려진 한계 (백로그)

**그룹 단위 컬링이라 "한 그룹이 매우 큰 경우"는 완화되지 않는다.** shadcn-admin의 `table.tsx`/`users-columns.tsx`처럼 수천 개 노드가 **하나의 그룹**에 속하면, 그 그룹이 뷰포트에 조금이라도 걸치는 순간 구성원 전체가 한 번에 펼쳐진다 — ADR-0012가 애초에 "그룹만" 재계산하기로 스코프를 잡은 것과 같은 한계다. 실측(§ 위 표)에서는 이 경우가 드러나지 않았는데, 대규모 단일 그룹은 fitView가 지도 모드로 떨어뜨려(P2) 애초에 펼쳐지지 않는 상태로 대부분의 상호작용이 일어나기 때문이다 — "그 큰 그룹으로 직접 줌인해 들어간 상태에서의 상호작용"은 이번 스코프에서 측정하지 않았다. 그룹 내부 서브 가상화(예: 큰 그룹 안에서도 뷰포트 안쪽 자식만 펼치기)는 후속 과제로 남긴다.
