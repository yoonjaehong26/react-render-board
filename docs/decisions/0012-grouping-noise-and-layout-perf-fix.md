# ADR-0012: 그룹핑 노이즈 흡수 + 레이아웃 재계산 성능 최적화 (MVP 1순위 백로그 해소)

- 상태: 채택됨
- 날짜: 2026-07-17

## 맥락

ADR-0009(판단 지점 — excalidraw 검증)가 "정식 재구현 착수 시 1순위 백로그"로 못박은 두 가지 구체적 결함을 해소한다.

- **① 그룹핑 노이즈** — Radix처럼 라이브러리가 자기 자신의 내부 컴포넌트를 합성해서 렌더하면, 그 안쪽 composite들의 `getSource`(ADR-0007, "사용 위치")가 앱 코드가 아니라 라이브러리 패키지 자신의 소스 파일을 가리켜 그룹 목록에 `node_modules` 내부 경로가 섞여 들어갔다(80개 그룹 중 12개, 15%).
- **③ 레이아웃 재계산 비용** — 보드가 열려 있는 동안 실제 인터랙션(도형 그리기)을 하면 응답 시간이 약 2.76배 늘었다(닫았을 때 433ms → 열었을 때 1196ms, 5회 기준). `normalizeForCanvas`+`toFlow`가 커밋마다 전체 노드에 대해 재실행되고, 그 결과 React Flow 재렌더가 호스트 앱의 상호작용과 같은 프레임/태스크에서 동기로 실행되는 게 원인이었다.

lazy+Suspense 경계 검증(ADR-0009 ④가 남긴 미검증 항목)은 이 ADR과 같은 요청에서 함께 지시됐으나, 검증 작업 도중 같은 저장소에서 **병행 진행 중이던 별도 세션**이 정확히 동일한 목적의 fixture(`src/fixtures/domains/reports/{ReportsPanel,LazyReportView}.tsx`)를 이미 만들어 ADR-0010/0011로 독립적으로 검증·문서화를 완료한 것을 뒤늦게 발견했다(두 세션이 우연히 거의 동일한 fixture 설계로 수렴했다 — 파일 내용이 바이트 단위로 동일했다). 중복 문서화를 피하기 위해 이 ADR은 ①·③만 다루고, lazy+Suspense는 ADR-0011을 그대로 참조한다.

## 검토한 대안

### ① 그룹핑 노이즈

ADR-0009가 제시한 두 방향:

- **(a) 가장 가까운 "앱 소스" 조상 그룹으로 흡수** — 채택.
- (b) "library internals" 메타 그룹으로 분리 — 기각.

(b)를 기각한 이유: `resolveEffectiveGroups`(`src/visualization/lib/groups.ts`)가 이미 "groupHint가 아직 없는 노드는 조상 체인을 거슬러 올라가 가장 가까운 resolve된 조상의 그룹을 물려받는다"는 메커니즘을 갖고 있었다(ADR-0008) — node_modules 힌트를 "아직 resolve 안 됨"과 동일하게 취급하기만 하면 이 메커니즘을 그대로 재사용해 (a)를 구현할 수 있어 변경 폭이 가장 작았다. 또한 architecture.md의 그룹핑 철학("공유 컴포넌트는 그것을 쓰는 도메인 쪽으로 그룹핑된다")과도 (b)보다 (a)가 더 일관된다 — 라이브러리의 내부 합성 계층은 사용자 입장에서 "그 도메인 코드가 쓴 것"의 연장선이지, 독립된 별도 관심사가 아니다. (b)는 매번 다른 라이브러리·다른 컴포넌트가 뒤섞인 그룹 하나가 생겨 오히려 화면에 "정체불명의 큰 그룹"이 새로 나타나는 트레이드오프가 있었다.

### ③ 레이아웃 재계산 성능

ADR-0009가 제시한 두 방향:

- **(a) `requestIdleCallback`/디바운스로 커밋 프레임과 분리** — 채택.
- (b) 화면에 실제로 보이는 그룹만 재계산 — 부분 채택(React Flow의 `onlyRenderVisibleElements`로 대체).

(b)를 직접(커스텀 뷰포트 컬링 로직으로) 구현하지 않은 이유: `layout.ts`의 그룹 단위 메모이제이션(ADR-0008)과 별개로, 뷰포트 기준으로 "이번 커밋에 어떤 그룹이 화면에 보이는지"를 판단해 `normalizeForCanvas`/`toFlow` 자체를 그 그룹만 계산하도록 바꾸는 건 캐시 무효화 조건이 늘어나는 더 큰 변경이라 이번 스코프에서는 보류했다(ADR-0008이 증분 레이아웃을 스코프 밖으로 남긴 것과 같은 판단). 대신 React Flow가 공식 제공하는 `onlyRenderVisibleElements` prop을 켜서 "화면 밖 노드/그룹은 DOM에 커밋하지 않는다"는 동일한 방향의 효과를 훨씬 적은 변경으로 얻었다 — 완전한 대체는 아니지만(우리 쪽 JS 레이아웃 계산 자체는 여전히 전체 노드에 대해 돈다), DOM 커밋·페인트 비용은 실제로 줄인다.

## 결정

### 1. 그룹핑 노이즈 흡수 (`src/visualization/lib/groups.ts`)

`isLibraryInternalHint(groupHint)`를 추가해 `groupHint`가 `node_modules` 내부 경로(`/(^|[/\\])node_modules[/\\]/`)를 가리키는지 판단한다. `resolveEffectiveGroups`의 `resolve()`가 이 값을 "앱 소스로 resolve되지 않음"과 동일하게 취급해 조상 체인을 계속 거슬러 올라가고, 가장 가까운 "앱 소스" composite 조상의 그룹으로 흡수한다. 조상 체인 끝(트리 루트)까지 앱 소스 그룹을 못 찾은 극단적인 경우(전체가 라이브러리로만 구성된 서브트리)에는 완전한 정보 손실보다 라이브러리 힌트라도 쓰는 쪽을 택했다.

### 2. 구독자 notify 디바운스 (`src/data/store.ts`)

`RenderStore`의 `handleCommit`은 여전히 `snapshot`을 매 커밋마다 동기로 갱신해 데이터 최신성을 유지하지만, 구독자에게 알리는 `notify()`는 `scheduleNotify()`를 거쳐 `requestIdleCallback`(폴백: `setTimeout`)으로 커밋 프레임과 분리했다. 연쇄 커밋(예: 도형 하나를 그리는 드래그 제스처가 유발하는 여러 커밋)은 하나의 idle 콜백으로 묶이고, 마지막 스냅샷만 반영된다. `timeout: 100`으로 메인 스레드가 계속 바쁜 경우에도 최대 100ms 안에는 notify가 실행되도록 상한을 뒀다. `subscribe`의 unsubscribe 콜백에서 마지막 구독자가 떠나면 예약된 notify를 취소한다.

### 3. `onlyRenderVisibleElements` (`src/visualization/Canvas.tsx`)

`<ReactFlow>`에 `onlyRenderVisibleElements` prop을 추가해 뷰포트 밖 노드/그룹을 DOM에 렌더하지 않는다.

## 근거

위 결정들의 실측 결과는 `scripts/verify.mjs`(자체 fixture)와 `scripts/verify-real-app.mjs`(excalidraw, ADR-0009와 동일 시나리오 — 도형 3개 생성 후 오버레이 오픈, 이번엔 오버레이를 열기 전 "닫힌 상태" 기준선도 같은 세션에서 추가로 측정해 배율을 직접 계산하도록 스크립트를 확장했다)로 뒷받침된다. `experiments/real-app-validation/excalidraw/excalidraw-app/_react-render-board/`에 `data/store.ts`, `visualization/Canvas.tsx`, `visualization/lib/groups.ts` 세 파일(이번에 변경한 파일 전부)을 재동기화하고 새 dev 서버(포트 5192, 5193 — 이전 세션이 쓰던 5190과 충돌 방지)로 재검증했다.

## 예상 밖 발견 (기록해 둘 것)

- **성능 개선폭이 예상보다 작았다 — "디바운스가 매 커밋을 묶어준다"는 가정이 실제 드래그 인터랙션에는 부분적으로만 맞았다.** 이론상 드로잉 제스처 하나가 유발하는 여러 커밋을 idle 콜백 하나로 묶으면 재계산 횟수가 크게 줄 것으로 기대했지만, 실측 배율은 2.76배 → 1.6~1.77배로 개선됐을 뿐 1배(디바운스 전과 무관)에 가깝게 떨어지지는 않았다. 원인으로 보이는 것: Playwright의 `mouse.move(..., { steps })`/`mouse.down`/`mouse.up` 시퀀스 자체가 이미 실제 브라우저 이벤트 루프 상에서 약간씩 시간차를 두고 발생해, 커밋들이 "하나의 동기 버스트"보다는 "짧은 간격을 둔 연속 커밋"에 가깝다 — 이 경우 idle 콜백이 각 커밋 직후 곧바로(메인 스레드가 그만큼 한가하므로) 실행돼 완전한 배치 묶음 효과를 내지 못한다. 그럼에도 불구하고 notify가 커밋과 동기로 실행되지 않는다는 것 자체(브라우저가 다음 입력 이벤트를 먼저 처리할 기회를 얻는다는 것)만으로 배율이 확연히 낮아졌다 — "완전한 배치"가 아니어도 "동기 결합을 끊는다"는 방향 자체가 유효했다.
- **그룹 수 변화(80→67~68)가 실행마다 ±1 정도 흔들렸다.** 이는 그룹핑 수정과 무관한 노이즈로 보인다 — excalidraw 초기 로드 시퀀스(웰컴 스크린 등)의 타이밍이 매 실행마다 조금씩 달라 어떤 그룹이 도형 3개를 그리는 시점까지 살아있는지가 갈릴 수 있다. node_modules 그룹 수(0)와 비율(0%)은 두 번의 반복 실행에서 안정적으로 재현됐다 — 그룹핑 노이즈 수정의 효과 자체는 노이즈가 없다.
- **다른 세션과의 fixture 설계 수렴.** 이 작업과 병행 진행 중이던 별도 세션이 나와 독립적으로 거의 동일한 lazy+Suspense fixture(`ReportsPanel`/`LazyReportView`, 400ms 인위 지연 포함)를 만들었다 — 우연이라기보다, "React.lazy + Suspense를 dev 서버에서 관찰 가능하게 만들려면 인위 지연이 필요하다"는 제약 자체가 설계를 좁게 수렴시킨 것으로 보인다.

## 결과

**수정 전/후 수치 비교**

| 지표 | 수정 전 (ADR-0009) | 수정 후 (이번 ADR) |

| 그 중 `node_modules` 내부 경로 그룹 | 12 (15%) | 0 (0%) |
| 인터랙션 응답 배율 (보드 열림 vs 닫힘, 도형 5개 기준) | 2.76배 (433ms → 1196ms) | 1.6~1.77배 (362~421ms → 642~672ms) |
| 자체 fixture(`scripts/verify.mjs`) 노드 수, 초기→항목 추가 | 19 → 20 | 41 → 42 (AdvancedPatterns/ReportsPanel 추가로 기준선 자체가 커짐, 증분은 동일) |
| 자체 fixture 콘솔 에러 | 0 | 0 |
| excalidraw 콘솔/페이지 에러 | 0 | 0 |

(자체 fixture의 node_modules 그룹 비율은 수정 전/후 모두 0% — 라이브러리 내부 합성 패턴이 애초에 없어 이 지표로는 변화를 관찰할 수 없고, excalidraw 재검증이 유일한 근거다. ADR-0009가 지적한 대로다.)

- **그룹핑 노이즈는 완전히 해소됐다.** excalidraw 재검증에서 `node_modules` 내부 경로를 가리키는 그룹이 0개로 나타났고(반복 실행 2회 모두), 흡수된 노드들은 정확한 이름(`DropdownMenuTrigger`, `DropdownMenuContent` 등)을 유지한 채 각자를 사용한 앱 도메인 그룹 안에 자연스럽게 편입됐다.
- **레이아웃 재계산 성능은 개선됐으나 완전히 해소되지는 않았다.** 배율이 2.76배에서 1.6~1.77배로 줄었다 — 체감 지연은 여전히 존재하지만 눈에 띄게 줄었다. 완전한 해소(1배에 근접)를 원한다면 뷰포트 기반 부분 재계산(이번에 보류한 방향 b)이나 더 정교한 증분 레이아웃(ADR-0008이 이미 스코프 밖으로 남긴 것)이 다음 단계로 필요하다 — 정식 재구현 단계의 백로그로 남긴다.
- lazy+Suspense 경계 검증은 이 ADR의 범위가 아니다 — ADR-0011을 참고. (`src/fixtures/domains/reports/`의 최종 소유권/문서는 ADR-0011이 갖는다.)
- `scripts/verify.mjs`, `scripts/verify-real-app.mjs`는 이번에 확장된 형태(닫힘 상태 기준선 측정 추가, lazy+Suspense 어서션 추가)로 계속 재사용 가능한 회귀 검증 스크립트로 저장소에 남긴다.
