# ADR-0020: 배포/설치 UX 방향 — npm 자동 설정 + 같은 페이지 플로팅 버튼

- 상태: 채택됨(번들러별 기술 검증은 [ADR-0021](0021-bundler-injection-feasibility.md)에서 완료 — 4개 번들러 모두 조건부 GO / **연결 방식 축 구현 완료: [ADR-0036](0036-distribution-connection-implementation.md)** — CLI init + Vite 플러그인 + 조건부 어댑터)
- 날짜: 2026-07-17

## 맥락 (Context)

`project-status.md`의 7-2절(구 6-2절 — 이후 문서 재구성으로 번호가 바뀜)은 "배포/설치 UX(npm 한 줄 설치 등)는 기능을 전부 완성한 뒤 논의하기로 의도적으로 보류"한다고 명시했다. 다만 정식 재구현을 준비하는 과정에서, "개발자가 이 도구를 어떻게 처음 만나고 켜는가"라는 진입 경험은 이후 설계할 여러 기능(검색, 코드 이동, 요소 클릭 연동 등)의 아키텍처 전제조건과 얽혀 있어, 방향성만 먼저 정해두기로 했다. 목표는 명확하다: **진입 장벽을 최대한 낮추되, 이미 조사된 고급 기능(`docs/research/2026-07-17-react-flow-ux-capabilities.md`)이 자연스럽게 얹힐 수 있는 구조**를 고른다.

이 결정은 두 개의 독립된 축으로 나눠서 검토했다.

1. **연결 방식** — 대상 앱에 계측 훅을 어떻게 걸 것인가.
2. **노출 위치** — 보드 UI를 어디에 보여줄 것인가.

## 검토한 대안 (Options)

### 연결 방식 축

- **npm 패키지 + 코드 수동 삽입** — 표준적이나(`TanStack Query Devtools` 선례) 개발자가 앱 소스에 직접 손대야 함.
- **npm + CLI 자동 초기화(`npx react-render-board init`)** — 채택. `react-scan`(이 프로젝트가 이미 의존하는 `bippy`와 동일 저자)이 실제로 검증한 패턴: CLI가 프레임워크를 감지해 dev 스크립트/설정을 자동으로 patch, 개발자는 손으로 아무것도 안 씀.
- **CLI 직접 실행형**(`npx react-scan@latest <url>`처럼 별도 브라우저 인스턴스를 띄우는 방식) — 기각. 조사 결과 이 방식은 "이미 열어둔 탭"이 아니라 **독립된 새 브라우저 창**을 띄우는 구조라, "탭 넘나들지 않기" 요구사항과 정면으로 충돌한다.
- **브라우저 확장** — 보류(폐기 아님). 번들러/프레임워크와 완전히 무관하다는 유일한 장점이 있으나, React-Sight가 겪은 실패(프로덕션 사이트를 정지시켜 Chrome 웹스토어에서 "안전하지 않음"으로 강제 차단된 사고)와 같은 리스크 프로필을 그대로 안고 있다. "localhost origin에서만 활성화"라는 안전장치로 완화는 가능하나, 스토어 심사·유지보수 부담은 여전히 남아 MVP 단계에서는 후순위로 둔다.
- **북마클릿/콘솔 스니펫** — 보류. 설치 자체가 없어 "일단 체험해보기" 채널로는 유효하지만, 새로고침마다 재주입해야 해서 일상 사용 도구로는 부적합.

### 노출 위치 축

- **같은 페이지 오버레이**(플로팅 버튼 → 클릭 시 React 포탈로 전체화면 확장, TanStack Query의 확장판) — 채택.
- **별도 웹페이지/라우트**(`/react-render-board`) — 보류. 화면을 넓게 쓸 수 있고 팀원에게 링크로 공유하기 좋다는 장점은 있으나, 계측 대상 페이지와 물리적으로 다른 탭/페이지가 되어 **크로스탭 통신(WebSocket 릴레이 등)이 별도로 필요**해지고, 사용자 입장에서도 탭을 오가야 하는 불편이 생긴다.
- **VSCode 웹뷰**(Microsoft Edge Tools for VS Code처럼 CDP로 실시간 페이지를 에디터 안에 스트리밍) — 보류. "UI를 어디에 그릴지"의 대안일 뿐, 브라우저 페이지와의 실시간 연결이라는 근본 요구사항을 대체하지 못한다. 코드 딥링크 등 에디터 통합 기능이 무르익은 뒤 재검토.
- **스탠드얼론 앱**(React DevTools의 Electron 버전처럼 원격 연결) — 보류. React Native나 임베디드 웹뷰처럼 "일반 브라우저 탭이 없는" 환경을 지원해야 할 때 재검토할 후보로 남긴다.

## 결정 (Decision)

**MVP 배포/진입 UX = npm 설치(자동화된 CLI `init`) + 같은 페이지(같은 탭) 플로팅 버튼.**

개발자는 `npx react-render-board init`을 한 번 실행하면 dev 스크립트/설정이 자동으로 구성되고, 이후 평소처럼 `npm run dev`만 실행하면 된다. 실행된 앱 화면 한 구석에 작은 플로팅 버튼이 나타나고, 클릭하면 **같은 탭 안에서** React 포탈로 렌더된 오버레이가 화면 전체를 덮으며 보드가 펼쳐진다. 별도 라우트나 새 탭/창은 쓰지 않는다.

## 근거 (Rationale)

1. **레이어 분리가 이 결정의 핵심 근거다.** Fiber 캡처(핵심 기능)는 React가 Fiber를 쓰는 한 번들러와 완전히 무관하지만, "자동으로 스크립트를 심어주는" 편의 레이어는 번들러(Vite/webpack/Turbopack/Rspack)마다 별도 통합이 필요하다는 게 이번 대화의 조사로 드러났다. Vite부터 시작하는 것은 이 프로젝트 자체의 스택과 일치하고, 2026년 시점 신규 React 프로젝트에서 가장 널리 쓰이는 선택지이기도 하다(주간 다운로드 4천만).
2. **"같은 페이지" 구조는 UX 취향이 아니라 아키텍처 요구사항이다.** React는 자신이 관리하는 모든 DOM 노드에 `__reactFiber$<random>` 프로퍼티로 Fiber 참조를 심어두고, `__REACT_DEVTOOLS_GLOBAL_HOOK__.renderers`의 `findFiberByHostInstance`로 "DOM 요소 → Fiber"를 즉시 조회할 수 있다(React DevTools의 "요소 선택" 기능이 쓰는 것과 동일한 메커니즘). 이후 로드맵에 있는 "웹 요소 클릭 → 다이어그램에서 바로 찾기" 기능은 이 조회가 **같은 JS 컨텍스트 안에서만** 가능해서, 보드가 다른 탭/페이지에 있으면 매번 크로스탭 메시징이 필요해진다. 처음부터 같은 페이지로 설계하면 이 비용이 아예 발생하지 않는다.
3. **react-scan이 이미 "zero-code-change CLI init" 패턴을 실제 서비스로 검증했다.** 같은 저자(`bippy` 제작자)가 만든, 이 프로젝트와 가장 가까운 선례라는 점에서 신뢰도가 높다.
4. **브라우저 확장을 후순위로 둔 것은 React-Sight의 실패를 그대로 반복하지 않기 위해서다.** `architecture.md`의 설계 원칙 1번("devtools-only 실행")과 결이 같다 — MVP 단계는 위험을 최소화하는 경로를 우선한다.

## 결과 (Consequences)

- **좋은 점**: dev-only 실행 원칙과 자연스럽게 부합해 프로덕션 사고 리스크가 구조적으로 없다. 같은 페이지 구조를 처음부터 택해 향후 고급 기능(요소 클릭 연동, React DevTools식 props/state 검사)이 추가 아키텍처 변경 없이 얹힐 수 있다.
- **트레이드오프**: "모든 프론트엔드 개발자"가 아니라 **"Vite를 쓰는 React 개발자부터"**로 스코프가 좁아진다. Next.js(Turbopack)/webpack/Rspack은 각각 별도 통합 공수가 필요하며, 특히 Turbopack은 자체 플러그인 API가 아예 없음이 확인되어([ADR-0021](0021-bundler-injection-feasibility.md)) Next.js `layout.tsx` 레벨의 프레임워크 우회가 필요하다.
- **검증 완료**: Vite/webpack/Rspack/Turbopack 각각에서 "앱 소스 코드를 전혀 안 건드리고 자동 스크립트 주입"이 실제로 되는지를 스파이크로 검증했다([ADR-0021](0021-bundler-injection-feasibility.md)) — 4개 번들러 전부 기술적으로 가능함을 확인했다(조건부 GO). 다만 Turbopack/Next.js는 플러그인 주입이 아니라 `layout.tsx` 같은 진입점 파일 패치가 필요해, 번들러별 어댑터 난이도가 균일하지 않다는 게 구체화됐다.
- **되돌리기 쉬움**: 연결 방식과 노출 위치를 독립된 축으로 설계했기 때문에, 나중에 한쪽만 바꿔 끼우기 쉽다 — 예를 들어 브라우저 확장을 추가로 병행하더라도 "같은 페이지 오버레이"라는 노출 위치 결정은 그대로 재사용된다. 반대로 노출 위치를 별도 웹페이지로 바꾸는 건(팀 공유 시나리오 등으로) 상대적으로 비용이 크다 — 요소 클릭 연동 같은 기능을 크로스탭 통신으로 다시 설계해야 한다.
- **관련 문서**: 이 ADR은 "어떻게 배포하고 진입할까"만 다룬다. 보드 안에서 어떤 기능(지도 모드, 검색, 주석, 코드 접근, 테마)을 만들지는 `docs/research/2026-07-17-react-flow-ux-capabilities.md`를 참고한다.
