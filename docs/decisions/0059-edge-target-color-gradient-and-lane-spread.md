# ADR-0059: 간선 타깃 도메인 색 그라데이션 + 레인 폭 확대 (허브 단색 뭉침 해소)

- 상태: 채택됨(구현 — 그라데이션·레인 폭 완료 / corridor-local 트랙은 유예)
- 날짜: 2026-07-18

## 맥락 (Context)

버스 병합([ADR-0054](0054-edge-routing-v3-coordination-design.md) Phase 2) 후에도 사용자 실측 피드백: **"흐름이 안 보인다. 비슷한 선들이 비슷하게 뭉쳐 구별이 거의 안 된다."**

진단(스크린샷 + 코드):
1. **뭉침의 정체는 버스가 아님.** 문제 선들은 `DemoApp.tsx` 그룹의 패널 9개가 각자 자기 그룹으로 내려가는 **1:1 크로스-그룹 간선**이다. 버스는 "한 출발 노드 → 여러 타깃"일 때만 합치는데, 여기는 출발 노드가 9개라 합칠 게 없다(개별 배선).
2. **전부 단색.** 색 = **출발 도메인**(ADR-0047)인데 9개 패널이 전부 같은 `DemoApp.tsx` 그룹 소속 → 전부 같은 파란색. 허브(한 도메인이 여럿을 렌더)에서 **출발색은 정보가 degenerate**하다 — 다 같은 출발이라 구별에 기여를 못 한다. 정보를 지닌 건 **타깃**(각자 다른 그룹으로 착지).
3. **공간 수렴.** 서로 다른 x에서 출발한 선들이 아래 몇몇 그룹으로 수렴하며 좁은 corridor에서 겹친다.

레이아웃(ADR-0056 부모 앵커)은 선을 짧게/트리형으로 만들지만 이 셋(색 언어·공간)을 못 고친다. "렌더 트리엔 역방향 간선이 없다(파이버=트리)"가 사실이라 트리 가정은 유효하나, **공유 컴포넌트=다중 부모(그룹 레벨 DAG)**만이 긴 선을 만든다(ADR-0056도 "공유 컴포넌트 레인"으로 남김).

## 결정 (Decision)

두 채널을 함께 손본다:

### A. 타깃 도메인 색 그라데이션 (핵심)

크로스-그룹 간선의 stroke를 **출발 도메인 색 → 타깃 도메인 색 선형 그라데이션**으로 그린다. 허브에서 나온 9개 파란 선이 각자 **다른 끝색**(CheckoutPanel·DataFlowPanel·…)을 얻어 "어디로 가는지"가 색으로 읽힌다. 출발색(어느 도메인이 호출했나)과 타깃색(어디로 가나)을 한 선에 동시에.

- 구현: `toFlow`가 크로스-그룹 간선 `data`에 `{sourceColorIndex, targetColorIndex, colorMode}`를 실어주고, `OrthoEdge`가 `userSpaceOnUse` `<linearGradient>`(source→target 좌표)를 그려 `stroke: url(#id)`로 칠한다.
- **CSS 시스템과 공존**: 인라인 stroke=url이 base 팔레트 CSS(`.edge-parent-palette-N`, no !important)를 이긴다. hover 혈통·추적/활동(`!important`)일 때만 solid 강조색으로 복귀 — focus 모드에선 단색이 오히려 적절(그 순간은 "이 한 경로"만 관심). dash(경계 점선)·opacity(깊이 감쇠)·width(혈통 강조)는 그대로. pending(색 미배정)이면 그라데이션 없이 기존 단색.

### A-2. 크로스-그룹 간선 실선화 (ADR-0047 선-스타일 채널 되돌림)

크로스-그룹 간선을 **점선 → 실선**으로 바꾸고 살짝 두껍게(1.75). 실측 피드백: 점선이 stroke를 조각내 **그라데이션 색 연속성을 끊어** "끝색이 갈리는지"가 안 읽혔다. 원래 점선은 ADR-0047의 "선 스타일 채널 = 그룹 내 실선/경계 점선"이었으나, **경계 넘김은 이미 프레임 밖으로 나가는 것으로 보이고 색 그라데이션이 정체성을 지녀 점선 채널이 중복**이라 실선으로 통일한다(3채널 중 선-스타일 채널을 색 그라데이션이 대체). 같은-그룹 hairline(실선)과는 색·두께로 구분된다.

### B. 레인 폭 확대 (down-payment)

전역 레인 오프셋을 ±12 → **±16**으로 넓혀 같은 corridor의 평행선이 덜 겹치게 한다. 상한은 `routeOrthogonal`의 `inset = lanePlacement(30) + laneOffset`가 `collideMargin(10)` 밖에 남는 범위(laneOffset > -20) 안이라 **프레임 관통을 안 만든다**.

## 근거 (Rationale)

- **카디널리티 색 언어의 빈틈 보완(ADR-0054 결정1).** "구조 간선=출발 도메인색"은 출발이 다양할 때만 정보가 산다. 허브 fan-out에선 출발색이 degenerate라, 타깃색을 그라데이션으로 얹어 정보를 회복한다 — 색 예산을 새로 쓰지 않고(같은 8색) 한 선에 두 정보를 겹친다.
- **사용자 분석과 일치.** "같은 색이라 어디서 온 지 모른다"를 사용자가 v3 착수 전 이미 예견했고, 그 답이 "타깃"임을 실측이 확인했다.
- **저위험.** 순수 프레젠테이션(데이터/레이아웃 불변). 그라데이션은 간선별 SVG라 노드 수와 무관. 레인 폭은 안전 상한 안.

## 유예 (Deferred) — Phase 3 본체

- **corridor-local sticky 트랙 배정(진짜 교차 최소화).** 지금 레인은 전역 x-순이라 특정 corridor 안 정렬이 아니다. 공유 수직 corridor를 식별해 그 안에서 sticky 트랙을 순서 배정하는 게 Phase 3의 핵심 — 큰 작업이라 분리한다. B는 그 전까지의 down-payment.
- **공유 컴포넌트 레인**(ADR-0056 후속, 다중 부모 긴 선) — 레이아웃 쪽과 함께.

## 결과 (Consequences)

- **바뀐 것**: `toFlow.ts`(크로스-그룹 간선 `data`), `OrthoEdge.tsx`(그라데이션 렌더), `Canvas.tsx`(레인 폭). 데이터/노드 좌표·색 팔레트 불변.
- **검증**: 유닛 331개 통과, `verify:edge-routing` 실측 9/9 ortho·프레임 관통 0·콘솔 에러 0(그라데이션·레인 확대가 렌더·배선을 안 깸). 시각은 `npm run dev`로 확인(허브 선들이 끝색으로 갈림).
- **되돌리기**: `OrthoEdge`에서 그라데이션 분기 제거 → 기존 단색 CSS. 레인 폭 상수 1개.
