# ADR-0018: P2 — 지도 모드 붕괴 수정(LOD) + P3 — 카메라 정체 수정

- 상태: 채택됨
- 날짜: 2026-07-17

## 맥락

ADR-0014(P2)와 ADR-0015(P3)가 남긴 두 결함을 함께 처리한다. 사용자 지시사항이 "같은 레이어"로 묶어 진행하라고 명시했고, 실제로 두 결함 모두 `Canvas.tsx`/`layout.ts`의 카메라·그룹 배치 로직에 걸쳐 있어 한 세션에서 다루는 게 자연스럽다. 또한 ADR-0017(P1)이 이미 "그룹을 뷰포트 기준으로 접고 펼치는" 메커니즘(`shouldExpandGroup`)을 만들어 둬서, P2의 LOD 요구("그룹을 실제 노드 대신 축약된 표현으로")를 그 메커니즘 재사용만으로 상당 부분 충족할 수 있었다.

- **P2 증상(ADR-0014):** `minZoom=0.05` 하드코딩 때문에 대규모(그룹 100+/노드 수천)에서 `fitView`가 요구하는 줌이 5%보다 낮아도 못 내려가 콘텐츠 대부분이 화면 밖에 남는다.
- **P3 증상(ADR-0015):** React Flow의 `fitView`가 마운트 1회성이라, 라우트 전환처럼 레이아웃 전체가 크게 바뀌어도 카메라가 안 따라간다(login 진입 시 226개 중 47개만 화면에). `layout.ts`의 `groupOrder`가 사라진 그룹을 pruning하지 않아 새 그룹이 점점 멀리 배치되는 것도 원인 중 하나로 지목됐다.

## 검토한 대안

### P2

- **(a) React Flow가 제공하는 옵션부터 확인한다(사용자 지시)** — `minZoom`을 낮추는 것으로 시작. 채택.
- **(b) 지도 모드에서 그룹을 축약 표현으로 그린다(LOD)** — ADR-0017(P1)이 이미 구현한 `shouldExpandGroup`(지도 모드에서는 뷰포트와 무관하게 전부 접음)이 사실상 이 요구를 충족한다 — **추가 구현 없이 재사용**.
- **React Flow를 다른 라이브러리로 교체** — 스코프 밖(사용자 지시, architecture.md 결정).

### P3

- **(a) 매 커밋 자동 refit** — 기각. 사용자가 수동으로 조정한 팬/줌을 계속 덮어써 버린다(사용자 지시사항이 명시적으로 경고한 트레이드오프).
- **(b) 그룹 집합이 "크게" 바뀔 때만 refit하는 휴리스틱 + `groupOrder` pruning** — 채택.

## 결정

### 1. `minZoom` 인하 (`src/visualization/Canvas.tsx`)

`minZoom={0.05}` → `minZoom={0.001}`. 순수 레이아웃 계산은 5,000노드까지도 병목이 아니었고(ADR-0014), 낮은 줌에서 개별 노드는 어차피 지도 모드로 접혀 그려지지 않으므로(위 ADR-0017) 바닥을 훨씬 낮춰도 추가 비용이 들지 않는다.

낮춰 보니 **두 번째 문제가 드러났다**: fitView가 실제로 1%까지 내려가 콘텐츠는 전부 화면에 들어왔지만, 캔버스 자체의 `transform: scale(zoom)`이 라벨 폰트까지 함께 눌러 텍스트가 사실상 안 보이는 크기가 됐다(기존 `.zoom-far` CSS의 20px 고정값은 zoom 5~55% 범위를 가정한 것이라 1% 같은 극단적인 줌은 감당하지 못했다). 그래서:

### 2. 라벨 역-스케일(counter-scale) — `src/visualization/components/GroupNode.tsx`

`useViewport()`로 현재 zoom을 읽어 라벨(`.group-node__label`/`.group-node__count`)에 `transform: scale(1/zoom)`을 적용한다 — 그룹 프레임 자체는 월드 좌표대로 계속 줄어들어야 "지도"가 성립하므로 그대로 두고, **텍스트만** 화면 기준 고정 크기(수학적으로 정확히 상쇄되므로 어떤 줌 레벨에서도 동일한 픽셀 크기)를 유지한다. 기존 `.zoom-far .group-node__label { font-size: 20px }` 같은 고정값 CSS는 제거했다(이중 스케일 방지).

### 3. 그룹 집합 변화 기반 auto-refit (`src/visualization/Canvas.tsx`)

`useAutoRefit(groupNames)`: 이전 커밋의 그룹 이름 집합과 현재 집합을 비교해 **생존율**(이전 그룹 중 지금도 남아있는 비율)을 계산한다. 생존율이 `REFIT_SURVIVAL_THRESHOLD = 0.3` 미만(=70% 이상이 새 그룹으로 교체)이면 `fitView({ duration: 400 })`를 호출한다 — "항목 추가"처럼 기존 그룹에 노드 하나 더하는 경우(생존율 1.0)는 절대 건드리지 않고, 라우트 전환처럼 서브트리 전체가 바뀌는 경우(생존율 0에 가까움)만 반응한다. 라우트 전환 도중 Suspense fallback → 실제 콘텐츠처럼 그룹 집합이 짧은 시간에 연달아 크게 바뀔 수 있어, 마지막 변화 후 `REFIT_DEBOUNCE_MS = 250`ms 잠잠해지면 한 번만 반영한다(ADR-0009/0012의 커밋 디바운스와 같은 패턴).

### 4. `groupOrder`/`groupOrderSet` pruning (`src/visualization/lib/layout.ts`)

`internalCache`(그룹 내부 배치 캐시)는 이미 매 커밋 사라진 그룹을 정리하고 있었지만 `groupOrder`/`groupOrderSet`(그룹의 상대적 배치 순서)는 그러지 않았다. `pruneOrder()`를 추가해 이번 커밋에 없는 그룹은 순서 배열에서도 제거한다 — 나중에 그 그룹이 다시 나타나면 `ensureOrder`가 "지금 시점의 맨 끝"에 새로 붙여줘서, 여러 라우트를 거치는 동안 순서 배열이 무한히 누적되고 새 그룹이 점점 카메라에서 멀어지는 문제(ADR-0015가 지목한 원인 중 하나)를 없앤다.

## 근거

`scripts/verify-real-app-shadcn-admin.mjs`(P2 — 지도 모드 스크린샷)와 `scripts/verify-routing.mjs`(P3 — berry-admin 라우트 전환, ADR-0015와 동일 시나리오)로 검증했다. 두 스크립트 모두 P1(ADR-0017)이 개별 컴포넌트 노드를 뷰포트 밖에서 만들지 않게 되며 깨진 기존 검증 로직(예: `.component-node__name` 텍스트로 라우트 간 차이를 비교하던 부분)을 그룹 라벨/`toolbar__count` 기준으로 다시 맞췄다 — 자세한 내용은 각 스크립트의 주석 참고.

## 알려진 한계 (백로그)

- **라벨 역-스케일은 개별 라벨을 읽을 수 있게 만들 뿐, 그룹이 아주 많을 때(수십~수백 개) 라벨끼리 겹치는 문제(declutter)는 풀지 않는다.** 그룹 프레임 자체는 줌이 낮아지면 화면상 서로 가까워지는데, 라벨은 고정 크기라 좁은 공간에 몰리면 겹친다. 이번 라운드의 shadcn-admin 재현에서 이 현상이 그대로 관찰됐다(스크린샷 참고) — 다만 ADR-0019(P4)로 노이즈 그룹을 흡수하고 나면 그룹 수 자체가 크게 줄어(berry-admin dashboard 기준 74→16개) 상당 부분 완화된다는 것도 함께 확인했다. 완전한 해결(우선순위 기반 라벨 숨김, 클러스터링 등)은 후속 과제로 남긴다.
- **auto-refit 임계값(생존율 0.3, 디바운스 250ms)은 이번 라운드의 관찰(berry-admin 라우팅 시나리오)에 맞춰 정한 값이다.** 다른 앱/다른 라우팅 패턴에서 이 값이 여전히 적절한지는 후속 실측이 필요할 수 있다.
