# ADR-0054: 간선 배선 v3 설계 — 중앙 coordination(버스 병합·교차 최소화·평행 색 줄기) + 색 언어 확정

- 상태: 채택됨(설계 + 색 언어 확정, 구현 단계별 — **Phase 1·2·3 완료**, 4 남음)
- 날짜: 2026-07-18

## 맥락 (Context)

[ADR-0051](0051-rule-based-cross-group-edge-routing.md) v2로 크로스-그룹 간선이 **간선별 독립 A***로 프레임을 피해 배선된다. 하지만 사용자 실측 피드백으로 세 가지가 남았다:

1. **간선끼리 교차** — 간선별 독립이라 다른 부모 경로가 채널에서 서로 가로지른다.
2. **버스 획 병합 미구현(7절 d)** — 같은 부모의 여러 간선이 트렁크+바+스텁으로 합쳐지는 회로도풍 정렬이 없다.
3. **props 흐름 평행 색 줄기 미구현([ADR-0045](0045-multi-props-flow-parent-colored-edges.md))** — 한 간선에 여러 흐름을 색선으로 나란히 그리는 완성형.

셋 다 **간선 간 좌표를 공유하는 coordination**(간선별 순수 함수를 넘어서는 전역 조율)이 필요하다. 또한 [ADR-0045](0045-multi-props-flow-parent-colored-edges.md)가 남긴 "공유 색 함수가 (a) 도메인색이냐 (b) 노드별 고유색이냐"를 여기서 확정한다.

이 ADR은 **설계도**다 — 색 언어를 확정하고, coordination 아키텍처와 단계를 정한다. 구현은 단계별로 얹는다.

## 결정 1 — 색 언어: **카디널리티로 갈린다** (ADR-0045 A/B 해소)

사용자와의 논의로 A/B는 "전역 택1"이 아니라 **간선 개수가 bounded냐 unbounded냐**로 갈리는 것으로 확정한다:

| | 간선 수 | 색 | 개별 구분 |
|---|---|---|---|
| **구조 간선** | 수백~수천 (unbounded) | **출발(부모) 도메인 색**(팔레트 8색, ADR-0047 그대로) | **레인(공간 분리) + hover** — 색 아님 |
| **props 흐름** | 사용자가 고른 **소수**(bounded) | **per-flow 고유색** | 색으로 직접 구분 |

**근거(지각 한계)**: 사람이 안정적으로 구분하는 카테고리 색은 ~8개다. 구조 간선은 수백 개라 간선당 고유색이 불가능(색 반복 → 오히려 혼란) — 그래서 **색은 대분류(도메인 8색), 정밀 구분은 공간(레인)**으로 한다(지하철 노선도 원리). 반면 props 흐름은 사용자가 개수를 스스로 제한하므로(3~5개) per-flow 고유색이 살아남는다.

- **왜 hover 이전에도 파악 가능한가**: 색만 정체성이 아니다 — **간선(선) 자체가 정체성**이라 끝점(출발 노드)을 눈으로 따라가면 된다. 레인은 선이 겹쳐 못 따라가는 걸 막고(공간 분리), 버스 병합은 따라갈 선 수를 줄인다(트렁크). hover는 밀집 구간의 **가속기**이지 유일 수단이 아니다. 극도 밀집에선 어떤 정적 그림도 한계라 hover/선택이 정답(모든 대형 다이어그램 툴 공통).
- **출발 도메인색이 도착보다 나은 이유**: 도착 도메인은 타깃 노드 색이 이미 보여줘 중복. 출발 도메인색은 노드만 봐선 모르는 비중복 정보("어느 도메인이 여길 호출했나").
- **사용자 원안(출발×도착 쌍 색)은 소규모 전용**: 손그림(간선 수십)에선 통하지만 자동화(수백~수천)에선 색 폭발로 무너진다 — 위 카디널리티 규칙이 그 자동화 버전이다.

## 결정 2 — 아키텍처: 간선별 독립 → **중앙 배선 pass**

버스 병합·트랙 순서·교차 최소화는 전역 정보가 필요하므로, **모든 크로스-그룹 간선을 한 번에 배선하는 pass**로 전환한다:

- Canvas가 크로스-그룹 간선 목록 + 프레임(장애물)을 받아 **`edgeId → 경로 점열` 맵**을 계산(`routeCrossGroupEdges(edges, frames)`, 순수 함수).
- `OrthoEdge`는 자기 경로를 **context 맵에서 읽기만** 한다(현재의 간선별 A* 대신). 레이아웃(프레임/노드 위치)이 안 바뀌면 맵을 memoize해 커밋마다 재배선하지 않는다(ADR-0017/0008 안정성 유지).
- 좌표의 순수 함수라 라이브 안정성은 그대로 상속. 단 **트랙 배정은 "sticky"** 로 — 새 간선이 떠도 기존 트랙 순서를 안 흔들게(ADR-0008 순서 고정의 간선 판).

## 결정 3 — 핵심 알고리즘(스케치)

1. **버스 그룹핑**: 크로스-그룹 간선을 **출발 노드별로** 묶는다. 한 출발의 간선들 = 하나의 버스(트렁크 1 + 채널 바 1 + 타깃별 스텁 N).
2. **채널/트랙 배정**: 같은 가로 거터(밴드 사이)를 쓰는 버스들에 **평행 y-트랙**을 배정한다. 순서는 출발 x(또는 타깃 x)로 정렬해 교차를 줄인다(VLSI left-edge / metro-line ordering, ADR-0029 §5 규칙 8). 트랙 간격은 lanePlacement 안쪽.
3. **경로 생성**: 각 버스에 대해 트렁크(출발→배정 트랙 y, 수직) + 바(트랙 y에서 수평, 프레임 회피는 A*가 거터로) + 스텁(바→각 타깃, 수직). 프레임 관통 회피는 v2 A*를 트랙 채널 위에서 재사용.
4. **props 평행 색 줄기**: 한 구조 간선 위를 여러 흐름이 지나면, 그 간선의 경로를 법선 방향으로 소량 오프셋한 **평행 색선 N개**로 그린다(흐름별 per-flow 색). 오프셋은 트랙 간격보다 작게.

## 단계 분해 (구현 순서)

- **Phase 1 — 중앙 pass 골격 ✅**: 크로스-그룹 간선 레인 오프셋을 출발 x 순으로 배정하는 중앙 테이블(`EdgeLanesContext`, hash 대체). 같은 출발=같은 레인. 회귀 verify 동일 출력.
- **Phase 2 — 버스 병합 ✅**: `routeCrossGroupBuses`(edgeRouting.ts) — 출발별로 묶어 **트렁크(수직 공유)+바(수평, 소스 프레임 아래 거터, 레인 y 분리)+타깃별 스텁**. `OrthoEdge`는 `EdgeBusPathsContext` 맵에서 자기 경로를 읽기만 한다(간선별 A* → 중앙 pass 전환, 결정2 실현). **안전장치**: 트렁크·바·스텁 중 하나라도 (자기 소스·타깃 프레임 제외) 다른 프레임을 관통하면 그 간선만 개별 A*로 폴백 → v2의 "관통 0" 유지(정밀 채널은 Phase 3). 유닛 4개(병합/폴백/레인분리/관통0) + `verify:edge-routing` 실측 6/6 ortho·관통 0. *시각 변화 큼(같은 부모가 한 줄기).*
- **Phase 3 — 트랙 순서 배정(교차 최소화) ✅**: `assignGutterTracks`([ADR-0060](0060-corridor-local-sticky-edge-tracks.md)) — 출발을 소스 프레임 y-층별로 묶어 x-순 barY 트랙으로 스택(같은 층 버스 바가 겹치지 않고 층층이). sticky(층 y·x 안정), 아래로만이라 프레임 침범 0, 넘침은 버스 폴백. tidy-tree(ADR-0058)가 거터를 1D로 만든 덕. *같은 층 교차 감소.* cross-layer·수직 corridor는 후속.
- **Phase 4 — props 평행 색 줄기**: 다중 추적(`tracks` 리스트, ADR-0045) + 간선당 평행 색선.

각 Phase는 독립 verify(교차 수·버스 병합 수·관통 0 유지)로 게이트한다.

## 위험 (Risks)

- **성능**: 전역 pass는 O(간선 수 × 격자). 크로스-그룹 간선은 소수(수십~수백)이고 memoize(레이아웃 불변 시 재계산 안 함)로 커밋당 비용 0에 수렴. 초대형은 Phase별 프로파일링.
- **라이브 안정성**: 트랙 배정이 매 커밋 안 튀게 sticky 필수(안 그러면 ADR-0008이 노드에서 푼 문제가 간선에서 재발). Phase 3의 핵심 설계 포인트.
- **교차 완전 제거 불가**: metro-line 최적화는 NP-hard라 근사(정렬 휴리스틱)만. "줄인다"이지 "0"이 아니다 — 남는 교차는 hover로.
- **되돌리기**: Phase 1이 전환점이라 되돌리려면 `OrthoEdge`를 다시 간선별 A*로. 순수 프레젠테이션이라 데이터/레이아웃 불변.
