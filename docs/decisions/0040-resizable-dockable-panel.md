# ADR-0040: 도킹 패널 크기 조절 + 위치 전환(하단/좌/우 사이드바)

- 상태: 채택됨(ADR-0025가 "이번 스코프 밖"으로 남긴 리사이즈/사이드바를 구현)
- 날짜: 2026-07-18

## 맥락 (Context)

[ADR-0025](0025-docked-panel-shell-amendment.md)는 보드를 전체화면 오버레이에서 화면 하단 도킹 패널(고정 45vh)로 바꾸면서, **"리사이즈 가능한 패널(사용자가 드래그로 높이 조절)은 이번 스코프 밖으로 남긴다"**고 명시하고 되돌리기 쉬움(국소적 CSS)까지 적어뒀다. UI QA에서 사용자가 이걸 요청했다: 하단 고정 대신 **높이 조절**, 그리고 **좌/우 사이드바**로도 붙일 수 있으면 좋겠다(나중에 모달/탭 분리 여지도).

## 검토한 대안 (Options)

### 크기를 무엇으로 저장할까

- **px 절대값** — 기각. 도킹 방향을 바꾸면(높이↔너비) px 의미가 달라지고, 창 크기가 바뀌면 비율이 깨진다.
- **화면 비율(fraction)** — 채택. 하단이면 화면 높이의, 좌/우면 너비의 비율(0.2~0.85)로 저장한다. 방향을 바꿔도 같은 값을 재사용하고 창 리사이즈에도 비율이 유지된다. CSS는 `--rrb-panel-size`를 `vh`/`vw` 단위로 받는다.

### 패널이 앱을 가릴 때 — 밀까 vs 덮을까

- **앱을 밀기(subject에 패딩 주입)** — 기각. 처음엔 패널 크기만큼 `.subject-root`에 패딩을 넣어 앱을 밀어 안 가려지게 했는데(ADR-0025의 "항상 보임" 연장), 사용자 피드백으로 방향을 뒤집었다: 이건 **관찰 도구가 관찰 대상의 레이아웃/CSS를 바꾸는 것**이다 — 앱의 반응형 breakpoint를 건드려 실제와 다른 렌더가 나올 수 있고, 실제 소비자 앱에선 "어느 요소에 패딩을 넣을지"도 불명확하고 깨지기 쉽다. 게다가 **크기 조절할 때마다 dev 페이지 비율이 바뀐다.**
- **오버레이 전용(앱을 안 건드림)** — 채택. 패널은 위에 떠서 덮기만 하고 앱 레이아웃은 그대로 둔다. 가려진 부분은 패널을 이동/크기조절/닫아서 본다 — react-scan / TanStack Query Devtools가 실제로 쓰는 모델. dev 페이지 CSS/비율을 절대 안 건드린다는 게 이 도구 철학(관찰만, 개입 안 함)에 더 맞다.

### 위치 전환 컨트롤을 어디에 둘까

- **Canvas 툴바에 버튼 추가** — 기각. 툴바는 Canvas(공유 파일)가 그리는데, 도킹은 패널 셸(BoardOverlay)의 상태라 계층이 섞인다.
- **안쪽 가장자리 중앙 알약** — 기각. 처음 중앙에 뒀더니 툴바/캔버스 내용과 겹쳐 거슬린다는 피드백.
- **안쪽 가장자리 "상단 모서리"** — 채택. 하단 도킹이면 위쪽 가장자리의 오른쪽 끝, 좌/우 사이드바면 안쪽 세로 가장자리의 위쪽 끝. 리사이즈 핸들과 별도 요소(더 높은 z-index)라 클릭이 리사이즈로 새지 않고, 툴바 내용과 안 겹친다.

## 결정 (Decision)

**패널에 드래그 리사이즈와 하단/좌/우 도킹 전환을 추가하되, 앱을 밀지 않는 오버레이 전용으로 하고 localStorage로 영속화한다.**

- 새 얇은 영속화 모듈 `panelLayoutPreference.ts`(colorModePreference.ts와 같은 패턴) — `{ dock: 'bottom'|'left'|'right', sizeFraction }`을 저장/복원, 비율은 `[0.2, 0.85]`로 clamp, 손상된 값/스토리지 접근 불가 시 기본값 폴백.
- **오버레이 전용**: `BoardOverlay`가 패널 요소에 `--rrb-panel-size`(하단=vh/좌·우=vw)를 직접 주고, `flow.css`의 `.board-panel--{dock}`이 이걸 읽어 위치/크기를 잡는다. **계측 대상 앱에는 아무 스타일도 주입하지 않는다**(예전 `.subject-root` 패딩 규칙 제거). body엔 "보드 열림" 신호(`rrb-board-open`)만.
- 리사이즈 핸들: 안쪽 가장자리 얇은 바를 `pointerdown`→`window`의 `pointermove`/`pointerup`으로 드래그. "안쪽으로 끌면 커진다"(하단=위/좌=오른쪽/우=왼쪽). 드래그 중엔 상태만, 놓을 때 한 번 영속화.
- 도킹 전환: 안쪽 가장자리 상단 모서리 알약의 3버튼(SVG 도형 아이콘 + aria-label). 다크모드 대응 포함.

## 근거 (Rationale)

- **관찰 도구는 관찰 대상을 바꾸지 않아야 한다.** 오버레이 전용이라 패널을 열든 크기를 바꾸든 dev 페이지의 레이아웃/CSS/반응형이 전혀 안 바뀐다 — 실측으로 확인(앵커 요소 좌표가 열기·리사이즈 전후 동일).
- **ADR-0025가 이미 "되돌리기 쉬움/국소적"이라고 예고한 대로**, 인터랙션 로직은 안 건드리고 셸 CSS + 얇은 상태만 추가했다. 데이터 스키마·Canvas·interactionStore는 불변.
- **비율 저장이 방향 전환과 창 리사이즈를 동시에 자연스럽게 처리**한다 — px였다면 둘 다 따로 보정해야 했다.
- **모달/탭 분리·F12식 앱 뷰포트 리사이즈로 가는 길을 막지 않는다** — 도킹을 `dock` 열거값으로 두었으니 나중에 `'modal'` 등을 추가하거나, 앱을 리사이즈 프레임에 감싸는 별도 기능을 얹는 게 국소적이다(후자는 이번 스코프 밖으로 남김).

## 결과 (Consequences)

- **바뀐 것**: 새 `panelLayoutPreference.ts`, `BoardOverlay.tsx`(상태·핸들러·리사이즈/도킹 UI·오버레이 전용), `flow.css`(`.board-panel--{dock}`/`__resize`/`__dock` + 다크), `index.css`(subject 패딩 주입 제거). 데이터/인터랙션 로직 불변.
- **검증**: `tsc` 클린, 유닛 테스트 258개 통과(`panelLayoutPreference` 6개 추가 — 라운드트립/clamp/손상값·비JSON 폴백/NaN). 실측으로 "패널 열기+리사이즈 후에도 앱 앵커 좌표 불변(오버레이가 앱을 안 밂)" 확인. 스크린샷으로 하단·좌·우 도킹 + 드래그 리사이즈 + 도킹 컨트롤 상단 모서리 배치 확인, 콘솔 에러 0.
- **트레이드오프**: 오버레이라 패널이 앱의 일부를 덮는다 — 가려진 부분은 패널 이동/크기조절/닫기로 본다(이 모델을 명시적으로 택함). 완전히 안 가리면서 앱을 보려면 "F12식 앱 뷰포트 리사이즈"가 필요한데, 앱을 프레임으로 감싸는 큰 작업이라 별도 후속으로 남겼다. 좌/우 도킹 시 우하단 FAB가 패널 위에 겹칠 수 있으나 z-index상 위라 조작엔 지장 없다.
- **되돌리기 쉬움**: 전부 셸 프레젠테이션 + 얇은 상태. 하단 고정으로 되돌리려면 dock을 'bottom' 고정하고 컨트롤을 숨기면 된다.
- **관련 문서**: 도킹 패널 셸 [ADR-0025](0025-docked-panel-shell-amendment.md), 플로팅 버튼/셸 [ADR-0037](0037-circular-floating-button-with-pick-satellite.md), 설정 영속화 선례 `colorModePreference.ts`(ADR-0027).
