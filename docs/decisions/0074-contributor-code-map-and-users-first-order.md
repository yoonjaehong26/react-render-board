# ADR-0074: 기여자용 코드 맵 문서 + "실사용자 우선" 확산 순서

- 상태: 채택됨
- 날짜: 2026-07-24

## 맥락 (Context)

소유자가 7-2(생존 전략 보류, ADR-0064)를 재개했다. 방향은 확정됐다: **오픈소스로 유지하며 외부 기여를 받아 장기 유지보수한다.** 배경 제약이 특수하다 — 소유자는 1년차 개발자이고 이 코드베이스를 AI 세션으로만 구현해 코드를 직접 읽지 않았다. 즉 (a) 외부 PR을 코드 심사로 판정할 수 없고, (b) 도메인 지식(React 생태계 엣지 케이스)이 부족하며, (c) 프로젝트 지식이 문서(ADR 74개 + project-status.md)에 외재화되어 있는 것이 사실상 유일한 유지보수 기반이다.

이 논의에서 두 가지 질문이 나왔다:
1. 커뮤니티(기여자) 유치와 실사용자 유치 중 무엇이 먼저인가?
2. "어떤 개발자가 와도 핵심 원리와 코드를 이해할 수 있는" 문서를 추가로 만들 것인가? (소유자 제안 — 단 문서-코드 동기화 부담을 우려)

기존 문서의 실태: `docs/architecture.md`가 구현 **이전의 설계 문서** 상태로 방치돼 있었다 — 훅킹 라이브러리가 "후보"(실제로는 ADR-0022에서 bippy 확정), 스키마가 "초안", 문장이 미래형. 즉 "코드가 하는 일을 다시 서술한 문서는 썩는다"는 동기화 문제가 이 레포에서 이미 한 번 실증됐다. 반면 ADR은 "그 시점의 결정" 기록이라 코드가 바뀌어도 거짓이 되지 않아 74개가 쌓이는 동안 썩지 않았다.

## 검토한 대안 (Options)

**질문 1 — 확산 순서:**
- A. 기여 인프라 선축조(CI, CONTRIBUTING, 거버넌스) 후 공개 홍보 — 기여자는 사용자 깔때기에서 나오므로 사용자 0명이면 무의미. 선행 프로젝트들이 죽은 "프로세스 곁가지 과투자" 패턴과 일치.
- B. **실사용자 유치 우선, 기여 인프라는 첫 외부 기여 신호가 올 때** — 실사용 제보가 지금까지 모든 중대 결함(ADR-0065~0071)을 잡았고, 소유자의 도메인 지식 부족을 사용자 환경 다양성이 메꾼다. CI+CONTRIBUTING은 필요해질 때 하루면 만든다.

**질문 2 — 기여자 문서:**
- A. 모듈별 API/알고리즘 상세 문서(typedoc 포함) — 코드의 "어떻게"를 복제하므로 빠르게 썩는다(architecture.md에서 실증). 엣지 배선 v3처럼 아직 움직이는 영역은 문서화 즉시 낡는다.
- B. **불변(invariant) 중심의 얇은 코드 맵 1~2페이지** — 레이어 경계, 디렉터리 지도, 깨면 안 되는 규칙, 검증 방법, ADR 내비게이션만. "어떻게"는 코드+테스트에, "왜"는 ADR에 두고 문서는 그 사이의 **지도** 역할만. 큰 틀(3-레이어, 스키마, 검증 문화)이 잡힌 지금이 쓸 수 있는 시점이고, 불변 규칙은 정의상 갱신 빈도가 낮아 동기화 부담이 작다.
- C. 새 파일 추가 — 기존 architecture.md와 역할이 겹쳐 이중화. 기각.

## 결정 (Decision)

1. **확산 순서는 실사용자 우선.** 오픈소스화 자체는 이미 완료(MIT, npm 0.2.x, 공개 레포) — 남은 것은 순서다: ① 기여자 진입 최소 준비(이 코드 맵, README 영어화, 환경 정보 필수 이슈 템플릿) → ② 공개 채널에 공유해 실사용자·이슈 유치 → ③ 첫 외부 기여 신호가 오면 CI(typecheck+vitest)와 CONTRIBUTING 추가.
2. **`docs/architecture.md`를 "기여자용 코드 맵"으로 전면 개편**(같은 커밋). 내용: 동작 원리 5줄, 3-레이어 디렉터리 지도(+"이 버그면 여기부터"), 불변 규칙 8개(각각 근거 ADR 링크), 검증 체크리스트, 추천 ADR 5개 경로. 상세 알고리즘 해설·모듈별 API 문서는 만들지 않는다.
3. **동기화 규칙을 CLAUDE.md에 1줄 추가**: 레이어 경계나 불변 규칙이 바뀌는 결정을 내리면 architecture.md도 같은 커밋에서 갱신. 그 외 변경엔 손대지 않는다.

## 근거 (Rationale)

- 기여자는 사용자 중에서 나온다. 인프라를 아무리 갖춰도 사용자 0명이면 기여자 0명 — 깔때기는 건너뛸 수 없다.
- 소유자가 코드 심사를 못 하는 약점은 (a) 기계 게이트(typecheck/vitest/verify), (b) 방향 판정 기준의 문서화(vision/ui-philosophy — 이미 있음), (c) 불변 규칙의 명문화(이번 코드 맵)로 보완한다. 코드 맵의 불변 규칙은 "이 PR이 헌법을 건드리는가"를 소유자가 코드를 다 읽지 않고도 판정하게 해주는 체크리스트다.
- 썩는 문서(코드 재서술)와 안 썩는 문서(결정·불변 기록)의 구분이 이 레포에서 실증됐으므로, 새 문서는 후자로만 제한한다.
- 코드 맵 작성 과정 자체가 소유자의 "척추 코드 읽기"(공개 API·스키마·cli/) 교재를 겸한다.

## 결과 (Consequences)

- architecture.md의 구 내용(라이브러리 후보 비교, fork 여부 논의)은 삭제됐다 — 해당 논의는 ADR-0002/0022와 prior-art 문서에 이미 보존되어 있어 정보 손실 없음.
- 동기화 부담은 "불변 규칙이 바뀔 때"로 한정된다. 불변 규칙 변경은 어차피 ADR감이므로 추가 프로세스가 아니라 기존 규율에 1줄 얹은 것.
- CI·CONTRIBUTING·영어 문서 전면화는 **의도적으로 지금 안 한다** — 각각의 트리거(첫 외부 PR, 실제 기여자 등장)가 명시됐으므로 잊히지 않는다.
- 위험: 실사용자 유치(공개 공유) 후 이슈가 늘면 소유자 응대 부담이 생긴다. "재현 요청은 정당한 응답"을 기본값으로 삼고, 환경 정보 필수 이슈 템플릿으로 삼각측량 비용을 낮춘다.
