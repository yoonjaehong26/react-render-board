# ADR-0016: P0 — `MAX_DEPTH` 형제-카운팅 버그 수정 (`src/data/serialize.ts`)

- 상태: 채택됨
- 날짜: 2026-07-17

## 맥락

ADR-0014가 실제 앱(shadcn-admin)과 합성 fixture 양쪽에서 독립적으로 재현하고 최상위 백로그로 못박은 결함이다. `serializeFiberTree`의 재귀 순회(`walk`)가 `depth`를 "자식 방향으로 내려갈 때"뿐 아니라 "형제로 넘어갈 때"도 증가시켰다 — `MAX_DEPTH(200)` 가드가 트리 깊이가 아니라 "한 부모 밑 형제 수"에도 그대로 적용돼, flat한 자식이 200개(실측: 실제 앱에서는 ~100개 근방부터) 넘는 흔한 패턴(행 많은 테이블, 긴 리스트)에서 나머지가 `console.warn`만 남기고 조용히 사라졌다. `docs/architecture.md`의 설계 원칙 2번("재귀 순회 가드 — 깊이 제한 + 방문 노드 캐시")이 요구하는 순환 참조 방어는 유지하면서, "깊이"와 "형제 개수"라는 서로 다른 두 개념을 분리하는 것이 목표다.

## 검토한 대안

- **(a) 형제 카운터를 별도 변수로 분리하되 재귀 구조는 그대로 유지, 형제 쪽 한도만 크게(예: 10,000) 잡는다** — 검토했지만 기각. `walk(fiber.sibling, ..., depth+1)`가 재귀 호출(그것도 함수의 마지막 문장이라 형태상 tail call)이라, V8이 tail call 최적화를 하지 않는 한 형제 하나당 JS 콜 스택 프레임을 하나씩 그대로 소모한다. 형제 카운터 상한만 올리면 "숫자 경고"는 없어지지만, 실제 대규모 flat 리스트(예: 500행 테이블 → 수천 형제)에서 여전히 "Maximum call stack size exceeded"로 죽을 수 있다 — architecture.md가 React-Sight의 실패 원인으로 명시한 바로 그 버그를 형태만 바꿔 재도입하는 셈이라 기각했다.
- **(b) 형제 순회를 반복문(iterative)으로 바꾸고, depth는 자식 방향 재귀에만 적용, 형제 전용 카운터는 "사실상 무제한이지만 진짜 순환 참조는 잡아내는" 큰 상한으로 별도 유지** — 채택.

## 결정

`src/data/serialize.ts`의 `walk`를 다음과 같이 재작성했다:

- `MAX_DEPTH = 200`은 그대로 두되, **자식 방향(`fiber.child`)으로 재귀 호출할 때만** `depth + 1`을 넘긴다. 형제 순회는 더 이상 `depth`를 소모하지 않는다.
- 형제 목록은 재귀가 아니라 `while (fiber) { ...; fiber = fiber.sibling; }` **반복문**으로 순회한다 — 형제 수가 몇천 개든 콜 스택은 O(1)로 유지된다.
- 형제 전용 가드 `MAX_SIBLINGS = 50_000`을 새로 추가했다. 합성 fixture(5,000개)와 실제 앱(shadcn-admin 9,240개 이상) 규모를 넉넉히 웃돌아 사실상 무제한에 가깝지만, 완전한 무제한은 아니다 — `fiber.sibling` 연결 리스트가 어떤 이유로든(예: bippy/React 내부 손상) 순환하면, "이미 방문한 id를 만나면 그 자리에서 중단"만으로는 무한 루프를 못 끊는 경우가 있다(A→B→C→A→B→C… 순환에서 매번 "다음 형제로" 건너뛰면 영원히 안 끝난다) — 이 카운터가 architecture.md 설계 원칙 2번이 요구하는 진짜 순환 참조 방어로 동작한다.
- `visited` Set 기반의 기존 순환 참조 방어(이미 방문한 fiber id를 다시 만나면 그 형제 체인 순회를 중단)는 그대로 유지했다.

## 근거

`scripts/verify.mjs`(자체 fixture, 회귀 없음 확인)와 `scripts/verify-real-app-shadcn-admin.mjs`(실제 앱, `/users?pageSize=100`)로 검증했다. 형제 순회를 반복문으로 바꾸는 것이 요청보다 한 걸음 더 나간 수정이지만, "형제 카운터를 크게 잡는 것"만으로는 재귀 depth 자체가 여전히 형제 수만큼 쌓여 스택 오버플로 위험이 그대로 남기 때문에, architecture.md의 원래 설계 의도(재귀 가드로 React-Sight식 크래시를 막는다)를 실제로 만족시키려면 반복문 전환이 필요하다고 판단했다.

## 결과

**수정 전/후 수치 비교 (shadcn-admin `/users?pageSize=100`, `scripts/verify-real-app-shadcn-admin.mjs`)**

| 지표 | 수정 전 (ADR-0014) | 수정 후 (이번 ADR) |
|---|---|---|
| 총 노드 수(진짜 total, `toolbar__count`) | ~8,950~9,240 (150/300/500 모두 이 근방에서 평평해짐) | **9,818** (더 늘어남 — 잘려나가던 나머지가 실제로 잡힘) |
| `MAX_DEPTH 초과` 콘솔 경고 | 588~3,189건 | **0건** |
| 자체 fixture(`scripts/verify.mjs`) 콘솔 에러 | — | 0 |

- **잘려나가던 데이터가 정확히 잡힌다.** pageSize=100에서 이전에는 `MAX_DEPTH`에 걸려 조용히 끊기던 나머지 노드까지 전부 직렬화되어, 진짜 총합이 9,240 → 9,818로 늘었다(+578, +6.3%) — ADR-0014가 "실제 pageSize=500에서의 진짜 fiber 수는 보고된 ~8,950보다 훨씬 클 것"이라 추정한 것이 그대로 확인됐다.
- **P1(다음 ADR) 작업의 정확한 기준선이 됐다.** 이 수정 이후의 노드 수(9,818 등)를 이후 모든 스트레스 테스트의 기준으로 삼았다.
- 이 수정은 **되돌리기 쉬운** 국소적 변경이다 — 데이터 스키마, 훅킹 방식 등 근본 결정과 무관한 순회 로직 내부 구현이다.
