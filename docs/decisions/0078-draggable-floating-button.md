# 0078. 플로팅 보드 버튼은 화면 안에서 드래그 이동·위치 기억을 지원한다

- 상태: 채택됨
- 날짜: 2026-08-25
- 관련: ADR-0020(같은 페이지 플로팅 버튼), ADR-0037(FAB+픽 위성), ADR-0040(도킹 패널 위치·크기)

## 맥락

보드는 호스트 앱의 레이아웃을 바꾸지 않는 오버레이여야 한다(ADR-0040). 하지만 우하단에 고정된
FAB는 좁은 반응형 뷰포트나 호스트 앱의 CTA·채팅 위젯과 겹칠 수 있다. 패널은 이미 크기와 도킹
위치를 조절할 수 있지만, 패널을 열기 전 진입점 자체를 피할 방법은 없었다.

## 검토한 대안

- 고정 우하단 유지 — 구현은 가장 단순하지만 겹침을 사용자가 해결할 수 없다.
- 코너 네 곳만 선택 — 예측 가능하지만 앱 UI가 꼭 코너에만 있는 것은 아니고, 좁은 화면에서
  충분한 회피 공간을 주지 못한다.
- FAB 묶음을 자유 드래그 — 필요한 자리로 바로 피할 수 있고, 기존 pointer 이벤트 기반 패널
  리사이즈와 같은 입력 모델을 쓴다.

## 결정

**메인 FAB와 요소 선택 위성을 하나의 묶음으로 드래그 이동 가능하게 하고, 위치를 화면 비율로
`localStorage`에 저장한다.**

- `pointerdown` 뒤 6px 이상 움직여야 드래그로 확정한다. 그보다 작은 입력은 기존 버튼 클릭으로
  보드 열기/닫기와 픽 모드 토글을 그대로 수행한다.
- 드래그 중에는 묶음 전체를 뷰포트 16px 여백 안에 clamp한다. `touch-action:none`으로 실제
  터치 환경에서 페이지 스크롤과 경쟁하지 않는다.
- 저장값은 이동 가능한 가로·세로 범위 각각의 0~1 비율이다. 창 크기나 DevTools 반응형 뷰포트가
  바뀌어도 상대적인 위치가 유지되고, 손상된 저장값은 기본 우하단으로 폴백한다.
- 메인 FAB의 hover 워드마크 확장은 드래그 중 잠시 접는다. 이동 중 묶음의 폭이 바뀌어 좌표가
  튀는 것을 막기 위함이다.

## 결과

- 앱 CSS·레이아웃·라우터는 여전히 변경하지 않는다. 상태는 `BoardOverlay`와 새
  `floatingButtonPreference.ts`에만 있고, RenderNode·interactionStore·Canvas는 불변이다.
- 사용자는 플로팅 버튼 묶음의 빈 곳 또는 버튼 자체를 끌 수 있다. 드래그 끝의 합성 click은
  소비하므로 의도치 않게 보드를 열거나 픽 모드를 켜지 않는다.
- 단, 키보드만으로 임의 좌표로 옮기는 기능이나 별도 "기본 위치로 되돌리기" UI는 이번 요구에
  포함하지 않았다. 저장소를 비우면 기본 우하단으로 돌아간다.
- `floatingButtonPreference` 유닛 테스트로 기본값·저장 왕복·경계 clamp·손상값 폴백을 검증한다.
