# UI Philosophy

## 핵심 질문

> 대규모 컴포넌트 구조를 어떻게 이해하기 좋은 UI로 만들까?

정확히는 "단순한 UI"가 아니라 **"필요한 순간에만 복잡도를 보여주는 UI"**다. 처음부터 다 단순화하면 정보가 사라지고, 처음부터 다 보여주면 스파게티가 된다.

## 원칙: Detail on Demand

큰 트리를 다룰 때의 표준 접근은 **semantic zoom**이다. 단순히 확대하면 커지는 게 아니라, 줌 레벨에 따라 **정보량 자체가 질적으로** 달라진다.

- 줌 아웃 → 큰 영역(도메인/폴더)만 보임
- 줌 인 → 실제 컴포넌트 노드가 드러남

## 그룹핑: 뭉치지 말고 영역으로 나눠라

그래프 시각화 문해력 연구에 따르면, 대부분의 사람은 여러 노드를 하나로 뭉치는 "super-noding"이나 엣지 번들링을 잘 못 읽는다. 반면 실제 노드를 유지한 채 **지역(region)으로 묶는** 지도형(map-like) 시각화가 과제 수행·기억·참여도 면에서 더 우수하다.

→ 컴포넌트를 뭉쳐서 숨기지 말고, **회색 박스 같은 시각적 경계로 영역만 나누고 실제 노드는 다 보이게** 둔다. (사용자가 예전에 손으로 그렸던 다이어그램이 정확히 이 방식이었다.)

## 대규모 구조를 다루는 3가지 축

1. **영역(region) 기반 그룹핑** — 폴더/도메인 단위로 시각적 경계만 그어주기 (뭉쳐서 숨기지 않음)
2. **점진적 공개(progressive disclosure)** — 줌 아웃에선 영역명만, 줌 인하면 실제 컴포넌트가 드러남
3. **검색으로 탈출구 마련** — 특정 컴포넌트를 바로 찾을 땐 지도보다 검색이 빠름 (React DevTools의 강점을 버리지 않음)

## UI 골격: 노드 에디터 + 지도 줌

세 가지 후보 철학을 검토했다:

| 철학 | 설명 | 대표 레퍼런스 |
|---|---|---|
| A. 지도(Map) | 줌에 따라 영역↔노드 | Obsidian Graph view |
| B. 노드 에디터 | 자유 배치 박스+선 (Figma식) | n8n, Unreal Blueprint |
| C. 파일트리 하이브리드 | 폴더 구조를 스윔레인으로 | CodeSee |

**결론: B를 기본 골격으로, A의 줌 동작을 얹는다.**

- 사용자가 Figma에서 편하게 느낀 감각(B)을 그대로 살린다.
- React Flow(xyflow)가 이 목적의 사실상 표준 라이브러리다.
- 여기에 semantic zoom(A)을 더해 대규모 스케일 문제를 해결한다.

## 참고 레퍼런스

- **xyflow `awesome-node-based-uis`** — 노드 기반 UI 총정리. 디자인 감각 잡기용.
- **Obsidian Graph view** — 클러스터링 + 줌 동작의 정석.
- **CodeSee** — 가장 가까운 직접 선례.
- **FigJam / Miro** — "박스+프레임으로 영역 나누기" 패턴의 원조.
- **React DevTools Profiler flamegraph** — 나중에 시간/성능 축을 추가할 때 참고.

## 되돌리기 쉬움 / 어려움 구분

바이브 코딩 중에도 이 구분을 지킨다:

- **되돌리기 쉬움 (자유롭게 실험)** → UI 인터랙션, 색상, 레이아웃, 클러스터링 알고리즘 디테일
- **되돌리기 어려움 (신중하게)** → 트리 데이터 스키마 (시각화 코드 전체가 여기 의존)
