# Vision

## 문제 정의

React 앱이 커지면 컴포넌트 계층이 깊어지고, prop 흐름이 복잡해지고, 상태 관리가 미로처럼 느껴진다. 코드만 읽어서 전체 구조를 파악하는 것은 특히 처음 보는 코드베이스에서 어렵다.

기존 도구들의 한계:

- **React DevTools** — 실시간 렌더 트리를 정확히 보여주지만, 좌측 사이드바의 들여쓰기 텍스트 리스트라서 "전체 그림"이 공간적으로 들어오지 않는다.
- **CodeSee 등 정적 분석 도구** — Figma 같은 캔버스를 제공하지만 `import` 관계 기반이라, 실제 렌더 구조(`children` prop, Context, 조건부 렌더링)와 어긋난다.
- **정적 JSX 파서 (rch, ReacTree 등)** — 실행하지 않고 코드만 분석해서 실시간이 아니다.

## 핵심 통찰

### 1. 렌더 트리 ≠ 의존성 트리

`import` 관계로 그린 다이어그램은 실제 부모-자식 렌더 관계와 다르다. 예를 들어 `<Card>{children}</Card>`처럼 `children`으로 JSX를 넘기는 경우, import에는 안 잡히지만 실제 렌더 트리에서는 명확한 부모-자식이다. 우리는 **실행 중인 실제 렌더 트리**를 대상으로 한다.

### 2. 타겟은 "익숙한 사람"이 아니라 "처음 온 사람"

시니어 개발자가 리스트 뷰로 충분한 이유는 "시니어라서"가 아니라 "그 코드베이스에 익숙해서"다. 같은 시니어도 새 회사 첫 주에는 지도가 없다. 공간적 시각화가 가장 큰 가치를 주는 순간은 **머릿속에 지도가 아직 없을 때**다.

- 익숙한 코드 디버깅 → 리스트 뷰로 충분 (이미 머릿속에 지도 있음)
- **처음 보는 코드 온보딩 → 공간적 배치가 훨씬 빠름** ← 우리의 타겟

### 3. 시각·공간 정보 처리는 유효한 인지 스타일

그림+텍스트를 함께 쓰면 이해·기억이 더 잘 된다(듀얼 코딩 이론)는 것은 심리학에서 꽤 검증된 결과다. 다이어그램 선호는 경험 부족의 신호가 아니라 정보 처리 방식의 차이다.

## 목표

- 새 코드베이스의 컴포넌트 구조를 **한눈에** 파악하게 한다.
- 실제 렌더 구조를 정확히 반영한다 (정적 분석의 부정확함을 피한다).
- 대규모 앱(수백~수천 컴포넌트)에서도 뭉개지지 않는다.

## 비목표 (Non-goals)

- React DevTools를 대체하지 않는다. (props/state 실시간 디버깅은 DevTools가 이미 잘 한다.)
- 성능 프로파일링 도구가 아니다. (최소한 MVP 범위에서는.)
- React 외 프레임워크를 지원하지 않는다.

## 성공 기준

이 프로젝트의 진짜 성공 질문은 "기술적으로 되는가"가 아니라:

> **"완성 후에도 이걸 계속 붙잡고 있을 동기가 있는가?"**

선행 프로젝트들이 죽은 이유가 기술이 아니라 "만든 사람들이 오래 유지할 동기가 없어서"였기 때문이다. ([`research/prior-art.md`](research/prior-art.md) 참고)

용도별 성공 기준:

- **포트폴리오/학습용** → 완성해서 남에게 보여줄 수 있으면 성공.
- **실사용 도구** → 방치돼도 오래 안 깨지는 구조로 설계 (버전 종속성 최소화).
- **커뮤니티 오픈소스** → "왜 선행 프로젝트들이 죽었는지"를 문서화해 다음 기여자가 같은 실수를 피하게 함.
